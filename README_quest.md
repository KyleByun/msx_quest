# MSX2 던전 탐험 (quest.rom)

Bard's Tale / Might and Magic / Wizardry 형태의 1인칭 던전 탐험. MSX2 SCREEN 5.

**동작하는 것**: 참고 화면을 그대로 옮긴 배경, 좌상단 96×96 던전 뷰, **원근이 적용된 벽돌 벽·바닥·천장**, 칸 단위 이동과 90도 회전, 벽 충돌, 옆길이 뚫린 것이 보이는 통로, **D&D 규칙으로 만든 파티 여섯 명**, **몬스터 그림 여섯 종**, **Bard's Tale 식으로 주고받는 d20 전투**, **오른쪽 창에 흘러가는 전투 기록**.

```powershell
.\build_quest.ps1                      # src/quest.asm -> build/quest.rom (32KB)
.\verify_quest.ps1                     # 창 없이 부팅해 build/quest.png 저장
.\verify_quest.ps1 -Keys "up,up,right" # 키를 넣은 뒤의 화면을 확인

uv run --with pillow python gfx\quest_convert.py   # 배경/런테이블/맵 재생성
uv run --with pillow python gfx\quest_rules.py     # D&D 표, 폰트, 몬스터 그림 재생성
uv run --with pillow python gfx\quest_preview.py   # 렌더러를 파이썬으로 똑같이 재현
uv run --with pillow python gfx\quest_diff.py .    # 에뮬레이터 화면과 픽셀 비교
```

| 키 | 동작 |
|---|---|
| ↑ | 한 칸 전진 (벽이면 제자리) |
| 스페이스 | 전투 걸기 / 한 라운드 진행 |
| (걷다가) | 여덟 칸에 한 번꼴로 마주친다 |
| ↓ | 한 칸 후진 (방향은 그대로) |
| ← / → | 제자리에서 90도 회전 |

누른 순간에만 한 번 반응합니다. 누르고 있어도 계속 가지 않습니다.

## 화면 배치

참고 스크린샷을 256×212로 줄여 16색으로 바꾼 뒤 RLE로 압축해 ROM에 넣고, 부팅할 때 한 번 풉니다.

| 영역 | 위치 |
|---|---|
| 던전 뷰 | 좌상단 1/4 안쪽, (16,8)에서 96×96 |
| 메시지(양피지) | 우상단 |
| 파티 상태 | 하단 |

던전 뷰 자리는 배경에서 비워 두었습니다. 파티 여섯 줄(`1 MORILDRANE` ~ `6 FASHOR`) 자리도 비웠습니다 - 참고 화면의 글자가 그대로 박혀 있어 값이 변하지 않기 때문입니다. 항목 이름 줄(`CHARACTER AC HIT PTS SPL PTS CL`)은 남겨 뒀습니다.

비운 자리가 전부 같은 값이라 압축이 잘 듭니다. 27,136 → **6,438**바이트입니다. 파티 줄을 비우면서만 3,994바이트가 줄었습니다.

> 지우기 전 배경은 `gfx/quest_bg_party.png` 에 남겨 두었습니다.

## 왜 실행 중에 레이캐스팅을 하지 않는가

"레이 트레이싱으로"라고 하셨는데, **광선을 실행 중에 쏘지 않습니다.** 대신 빌드할 때 한 번 풀어 둡니다. 이유는 이렇습니다.

칸 단위 이동에 90도 회전만 있으면, 화면에 나올 수 있는 벽면의 모양은 **서 있는 위치와 무관하게 언제나 같은 사다리꼴 몇 개**입니다. 광선을 쏘아 얻을 결과가 상수라는 뜻입니다. 그래서 파이썬이 미리 다 풀어서 표로 만들어 두고, Z80은 "이 칸이 벽인가"만 봅니다. 실행 중에 나눗셈도 곱셈도 하지 않습니다.

칸마다 실제로 광선을 쏘는 방식(Wolfenstein 3D)은 같은 답을 훨씬 비싸게 구하는 셈이고, 8비트에서 "이동이 쾌적해야 한다"는 요구와 정면으로 부딪힙니다. 지금 방식은 그 요구를 그대로 만족합니다.

굳이 실행 시간 레이캐스팅이 필요해지는 때는 **격자에 맞지 않는 벽(대각선), 칸마다 다른 벽 텍스처, 자유 각도 회전**을 넣을 때입니다. 그때는 말씀해 주세요.

## 기하 구조

소실점은 뷰포트 한가운데 (64,56). 경계는 눈에서 거리 z만큼 떨어진 평면이고 반폭은 1/z로 줄어듭니다.

| 경계 | 반폭 | 뜻 |
|---|---|---|
| 0 | 48 | 근평면 = 화면 가장자리 |
| 1 | 36 | 1칸 앞 |
| 2 | 18 | 2칸 앞 |
| 3 | 12 | 3칸 앞 |
| 4 | 9 | 4칸 앞 |
| 5 | 7 | 5칸 앞 |

**경계 1을 화면 가장자리보다 12픽셀 안쪽에 둔 것이 중요합니다.** 처음에 둘을 같게 했더니 바로 앞이 벽일 때 화면이 초록 한 색으로 꽉 차 버렸습니다. 지금은 그 12픽셀에 **내가 서 있는 칸**의 바닥·천장·옆벽이 테두리처럼 보여서, 막다른 길에서도 화면이 읽히고 **옆에 길이 있는지도 바로 보입니다.**

구간 j(0~4)는 경계 j와 j+1 사이이며 j칸 앞의 칸에 해당합니다. j=0이 내가 선 칸입니다.

## 벽 텍스처

`스크린샷 2026-08-20 102740.png` 의 벽돌 무늬를 씁니다. 원본을 재보니 가로 줄눈 주기 6(벽돌 4 + 줄눈 2), 벽돌 폭 12, 한 줄 걸러 반 칸씩 엇갈리는 규격이었습니다. JPEG 잡티가 많아 그대로 쓰지 않고 **같은 규격으로 12×12 타일을 다시 그렸습니다** (`gfx/quest_tex.py`).

**원근은 빌드할 때 이미 다 적용해서 픽셀로 구워 둡니다.** 벽면 모양이 상수이므로 그 위에 입히는 텍스처도 상수라는 점이 핵심입니다. 화면 좌표에서 텍스처 좌표를 구하는 계산(원근 나눗셈 포함)을 파이썬이 전부 풀어 놓고, Z80 은 바이트를 옮기기만 합니다.

투영은 `화면좌표 − 중심 = 72 × 월드좌표 / z` 입니다. 각 면은 이것을 역으로 풉니다.

| 면 | 거리 z | 텍스처 좌표 |
|---|---|---|
| 좌/우 벽 | `36 / |화면x − 중심x|` | u = z, v = 높이 |
| 바닥/천장 | `36 / |화면y − 중심y|` | u = 가로 위치, v = z |
| 정면 벽 | 거리 d (상수) | u = 가로, v = 높이 |

거리에 따라 어두워지고, 왼쪽에서 빛이 오는 것으로 쳐서 우벽이 좌벽보다 어둡습니다. 이 명암이 원근을 읽게 하는 가장 큰 요소입니다.

벽돌색은 **순회색**으로 맞췄습니다. 원본이 (169,168,171)로 살짝 푸른데 그대로 두면 양자화가 회색 계단 대신 푸른 색을 골라 화면에 얼룩이 생겼습니다.

전송은 **`outi`** 를 씁니다. `outi(16) + nop(4) + jp nz(10) = 30 T-state` 로 화면이 켜져 있는 동안 V9938 이 요구하는 29 를 넘깁니다. 즉 **단색으로 칠하는 것과 사실상 같은 속도로 그림을 옮깁니다.**

### 줄눈 두께는 텍스처 배율이 정한다

처음에는 `TEX_PER_CELL = 24` 였습니다. 가장 가까운 벽은 한 칸이 화면 96픽셀에 걸쳐 보이므로 확대율이 **4배**가 되고, 줄눈 2텍셀이 화면에서는 **8픽셀짜리 검은 띠**로 벌어졌습니다. 벽돌 사이가 뻥 뚫려 보인 이유입니다.

`TEX_PER_CELL = 96` 으로 올리면 가장 가까운 벽에서 1:1 이 되어, 줄눈 1텍셀이 화면에서도 1픽셀입니다. 벽돌 규격도 같은 비율로 키웠습니다(24x11, 줄눈 1, 타일 24x24). 원본 스크린샷의 비율(벽돌이 줄눈보다 훨씬 두껍고 한 줄 걸러 반 칸 엇갈림)은 그대로입니다.

### 옆길로는 무엇이 보이는가

광선을 따라가 보면 답이 나옵니다. 구간 j 의 오른쪽 벽이 없다고 하면, 그 자리를 지나는 광선은 기울기 `s = dx/P` 로 `x = 0.5` 를 `z = 0.5/s` 에서 통과해 옆 통로로 들어갑니다. 그다음 무엇에 부딪히는가가 핵심입니다.

옆 통로의 바깥벽(`x = 1.5`)까지 가려면 `z = 1.5/s` 여야 하는데, 그 전에 **`z = j+1` 평면을 먼저 만납니다.** 거기서 광선의 가로 위치는 `s*(j+1)` 이고 이것은 언제나 1.0 이하라 옆 통로 안입니다.

> **옆길로 보이는 것은 대각선 앞칸의 정면입니다.** 정면 벽과 똑같은 `z = 상수` 평면이라 원근 나눗셈도 상수여서, `bake_front(j+1, ...)` 를 그대로 쓰고 어둡게만 하면 됩니다.

위아래 경계도 정확히 떨어집니다. 광선이 천장(`y = 0.5`)에 닿는 것은 `z = 36/|dy|` 이므로 `|dy| > 36/(j+1)` 이면 벽보다 천장을 먼저 만나는데, `36/(j+1)` 이 바로 `HALF[j+1]` 입니다. 즉 **경계가 깊이 j+1 사각형의 반높이와 같습니다.**

### 뚫린 느낌은 밝기가 아니라 모양이 만든다

여기서 세 번 틀렸습니다. 세 번 다 "어둡게 하면 뚫린 것처럼 보이겠지"라고 생각한 게 원인이었습니다.

**1차 — 바닥/천장만 어둡게 이어 그림.** 뚫린 자리 **전체가 회색 판**으로 덮여 그림자 진 벽처럼 보였습니다.

**2차 — 맞은편 벽만 그리고 띠 바깥은 검정.** 위아래가 **커다란 검은 삼각형**이 되어 이번에도 그림자로 읽혔습니다. 특히 `j = 0`(내가 선 칸의 옆이 뚫린 경우)에서 심했습니다. `d = 1` 이라 맞은편 벽의 벽돌 크기가 바로 옆 벽과 **똑같고**(둘 다 화면 18픽셀), 띠도 `HALF[1] = 36` 이라 거의 전체 높이를 덮습니다. 같은 크기의 벽돌이 조금 어둡게 붙어 있는 셈이니, 밝기를 어떻게 조절해도 그림자입니다.

**3차 — 바닥/천장은 이어 그리되 맞은편 벽만 어둡게.** 막다른 곳에서 **정면 벽 좌우에 검은 띠**가 생겼습니다. 이게 결정적인 힌트였습니다.

> 막다른 곳의 정면 벽과 그 옆의 뚫린 자리는 **z 가 같은 한 평면**입니다. 앞에서 유도했듯 옆길로 보이는 것은 `z = j+1` 평면인데, 막힌 구간에서는 `j+1` 이 곧 정면 벽의 깊이입니다. 한쪽만 어둡게 하면 같은 벽의 절반만 그늘진 꼴이고, 실제로 그 칸까지 걸어가서 보면 밝은 벽입니다.

그래서 결론이 오히려 단순해졌습니다.

```python
def bake_open(j, x, y):
    d = j + 1
    dy = y - G.CY
    if abs(dy) >= G.HALF[d]:                    # 옆 통로의 천장/바닥
        c = bake_floor(j, x, y) if dy > 0 else bake_ceil(j, x, y)
        return (0, 0, 0) if c is None else c
    return bake_front(d, x, y)                  # 대각선 앞칸의 정면
```

**옆길로 보이는 것은 "그 벽이 없었다면 보였을 그림" 그대로입니다.** 밝기 보정이 하나도 없습니다.

그래도 벽과 헷갈리지 않습니다. 구분해 주는 것은 밝기가 아니라 모양이기 때문입니다.

| | 맞은편 벽 (뚫린 자리) | 옆벽 (막힌 자리) |
|---|---|---|
| 평면 방향 | 정면을 향함 | 비스듬함 |
| 벽돌 | 크기가 고름 | 소실점 쪽으로 늘어남 |
| 위아래 | 바닥/천장이 옆으로 빠짐 | 벽이 그대로 이어짐 |

참고로 깊이에 따른 벽돌 크기는 이렇습니다.

| 깊이 | 벽돌 하나가 화면에서 |
|---|---|
| z = 1 | 18 픽셀 |
| z = 2 | 9 픽셀 |
| z = 3 | 6 픽셀 |

> 이 계산은 **대각선 칸(옆 1, 앞 j+1)이 벽이라고 가정** 합니다. 실제로 거기가 뚫려 있으면 더 멀리까지 보여야 하지만, 지금은 그냥 벽으로 보일 뿐입니다. 그 경우까지 구분하려면 실행 중 상태가 더 필요한데, 화면에서 그 자리는 몇 픽셀이라 값을 못 합니다.

### 바닥과 천장의 검은 가로선 - 텍셀 하나를 콕 집어 오면 안 된다

바닥과 천장에 검은 가로선이 몇 줄 뚝뚝 생기는 문제가 있었습니다. 원인은 줄눈을 **점으로 찍어 가져온** 것이었습니다.

바닥의 텍스처 세로 좌표는 `v = 96 x 36 / dy` 라서, 화면에서 한 픽셀 내려갈 때 `v` 가 얼마나 변하는지가 `dy` 에 따라 크게 달라집니다.

| 화면 위치 | 한 픽셀이 덮는 텍스처 | 결과 |
|---|---|---|
| 아래쪽 (`dy=47`) | 1.6 텍셀 | 줄눈 1 텍셀이 제 두께로 보인다 |
| 지평선 근처 (`dy=17`) | 12 텍셀 | 줄눈을 통째로 맞거나 통째로 건너뛴다 |

즉 먼 바닥에서는 한 픽셀이 텍스처 수십 줄을 덮는데 그중 **한 점만** 집어 옵니다. 우연히 줄눈에 걸린 줄은 화면 폭 전체가 새까맣게 되고, 안 걸린 줄은 줄눈이 아예 없습니다. 그래서 매끄러운 계조 대신 검은 줄 몇 개가 뚝뚝 생겼습니다.

답은 그 픽셀이 **덮는 넓이만큼 평균** 내는 것입니다(상자 필터). 굽는 시점에 하는 일이라 실행 중 비용은 **0** 입니다.

빨리 평균 내려고 타일의 누적합표를 만들어 둡니다. 상자가 타일 몇 장을 걸쳐도 덧셈 네 번이면 끝납니다. 타일은 텍셀마다 색이 일정한 계단 함수이므로 그 이중적분은 텍셀 한 칸 안에서 겹선형이고, 따라서 **네 정수 모서리를 겹선형 보간하면 분수 좌표의 적분값이 근사가 아니라 정확히** 나옵니다.

이 정확도가 중요했습니다. 처음에는 상자를 바깥 텍셀 경계까지 넓혀서 평균했는데, 한 픽셀이 1.33 텍셀을 덮는 정도(가장 가까운 벽이 그렇습니다)에서도 상자가 3 텍셀로 부풀어 벽돌 무늬가 뭉개졌습니다.

**그리고 이 필터는 바닥과 천장에만 겁니다.** 검은 가로선이 생긴 것은 바닥과 천장입니다. 벽은 세로 방향이 화면과 거의 1:1 이라 줄눈이 제 두께로 보이고, 압축되는 것은 가로 방향인데 그쪽 줄눈은 세로선이라 가로로 이어지는 검은 띠를 만들지 않습니다. 벽에도 걸어 봤더니 벽돌 무늬가 눈에 띄게 물러져서 되돌렸습니다.

### 자료 구조 - 좌우 벽만 픽셀 블록을 두 개 갖는다

같은 자리에 벽일 때와 뚫렸을 때 두 가지 그림이 필요한데, 렌더러는 포인터 하나로 스트림을 훑고 있었습니다. 그래서 **좌우 벽 런에만 픽셀 블록을 두 개** 붙였습니다. 천장/바닥/한가운데는 하나뿐입니다. 렌더러는 상태에 따라 첫째를 그리고 둘째를 건너뛰거나, 첫째를 건너뛰고 둘째를 그립니다. 포인터는 여전히 하나입니다.

면 상태가 여섯 가지로 늘었습니다.

| 상태 | 뜻 |
|---|---|

### 전투

스페이스로 전투를 걸고, 다시 누르면 한 라운드씩 진행합니다.

```
d20 을 굴린다
20 이면 무조건 명중, 피해 주사위를 두 배로
1 이면 무조건 빗나감
그 밖에는 d20 + 공격보정 >= 상대 AC 이면 명중
```

라운드는 원본과 같이 **영웅 전원 -> 몬스터 전원** 순입니다. 대상 고르기만 단순하게 했습니다(영웅은 살아 있는 첫 몬스터, 몬스터는 살아 있는 영웅 중 아무나). 원본의 AI 는 격자 위 거리 계산이라 여기서는 쓸 수 없습니다.

난수는 16 비트 xorshift 입니다. 주사위를 굴릴 때 8 비트 난수를 면 수로 나눈 나머지를 쓰면 `256 mod 20 = 16` 만큼 앞쪽 값이 자주 나와 d20 에서 6% 나 치우칩니다. 16 비트를 나누면 `65536 mod 20 = 16` 이라 0.05% 로 떨어져서 사실상 없습니다.

## 글자 찍기

참고 화면의 글자를 재어 보니 한 칸이 가로 6 픽셀이었습니다. 그래야 하단 파티 줄(이름 + 수치 여섯 + 직업 약자)이 256 픽셀에 들어갑니다. 그래서 **6x8 폰트**를 새로 그렸습니다(ASCII 32~90, 59 글자, 472 바이트).

폰트는 한 줄 8 비트인 1bpp 인데 화면은 4bpp 입니다. 니블 하나(픽셀 넷)를 두 바이트로 바꾸는 **32 바이트짜리 표를 RAM 에** 두고, 글자색/바탕색이 바뀔 때만 다시 만듭니다. 하단은 회색 바탕에 검정, 오른쪽 양피지는 크림 바탕에 검정입니다.

글자는 6 픽셀 간격으로 찍지만 실제로는 8 픽셀을 씁니다. 오른쪽 두 칸은 다음 글자가 덮으므로 겹쳐도 됩니다. **간격이 짝수라 x 가 늘 짝수로 남고**, 덕분에 바이트 경계에 딱 맞아 시프트가 한 번도 필요 없습니다.

## blueMSX 에서 멈춘 이유 - RAM 을 다 지우지 않았다

openMSX 에서는 멀쩡한데 blueMSX 에서 화면에 노란 가로줄 두 개가 그어지고 조작이 먹지 않는 증상이 있었습니다.

원인은 **초기화하지 않은 RAM** 이었습니다.

```asm
    ld hl, Vars                 ; 예전 코드
    ld de, Vars + 1
    ld bc, VarsEnd - Vars - 1   ; 0xC000 ~ 0xC00E 만!
```

`Vars` 는 0xC000~0xC00E 뿐이고, **`BattleOn`(0xC13C), `MonKind`(0xC16F) 같은 값은 0xC100 위쪽에 있어서 켤 때 그대로 쓰레기**였습니다. openMSX + C-BIOS 는 RAM 이 0 으로 켜져서 우연히 돌아갔을 뿐입니다.

RAM 이 다른 값으로 켜지는 기계에서는 이렇게 됩니다.

1. `BattleOn` 이 0 이 아니다 → 부팅하자마자 "전투 중"
2. `HandleInput` 이 전투 중에는 스페이스만 받으므로 **이동 키가 전부 무시된다** → 멈춘 것처럼 보인다
3. 메인 루프가 쓰레기 `MonKind` 로 `DrawMonsterPic` 을 부른다 → 표 밖을 읽어 엉뚱한 뱅크와 주소를 잡고 → **화면에 줄이 그어진다**

노란 줄의 색이 팔레트 15번(182,182,73)이었던 것이 결정적인 단서였습니다. `0xFF` 한 바이트가 픽셀 두 개짜리 15번이고, 본체 뱅크의 남는 자리를 `0xFF` 로 채워 두었기 때문입니다.

### 재현과 확인

openMSX 에서 `Init` 에 중단점을 걸고 0xC000~0xC2FF 를 0xFF 로 채운 뒤 계속 돌려서 **같은 화면을 그대로 재현**했습니다. 이동 키를 눌러도 좌표가 변하지 않는 것까지 같았습니다.

고친 뒤 같은 시험에서 정상 부팅, 이동, 전투가 모두 됩니다.

```asm
    ld hl, RamStart             ; 작업 영역 **전체**를 0 으로
    ld de, RamStart + 1
    ld bc, RamEnd - RamStart - 1
```

### 그림 그리기에 방어선도 넣었다

값이 깨져도 폭주하지 않도록 두 군데를 막았습니다.

- 종류 번호가 표 밖(`>= MONSTER_N`)이면 그냥 돌아간다
- 런 길이가 0 이면 줄 끝으로 본다

**길이 0 이 특히 위험했습니다.** `ld b,0` 이 되어 `outi` 가 256 번 돌고, 게다가 자리가 앞으로 가지 않아 같은 자리를 끝없이 다시 그립니다. 0 으로 채워진 빈 뱅크를 가리키면 정확히 그 꼴이 됩니다.

> **교훈**: RAM 이 0 으로 켜진다고 가정하면 안 됩니다. 실기에서는 켤 때 값이 정해져 있지 않습니다. `ORG` 를 여러 번 써서 RAM 을 나눠 잡았다면, 지우는 코드도 그만큼 늘려야 합니다.

## 128KB ASCII8 매퍼

몬스터 그림 여섯 장이 접어도 **8,338 바이트**입니다. 32KB 카트리지의 남은 자리가 9.8KB 였으니 그림만으로 거의 다 차 버려서 128KB 로 늘렸습니다.

| 뱅크 | 내용 | 실행 중 자리 |
|---|---|---|
| 0~2 | 코드와 늘 필요한 자료 (23,256 / 24,576 바이트) | 0x4000-0x9FFF 고정 |
| 3~4 | 몬스터 그림 (8,338 바이트) | 0xA000-0xBFFF 에 번갈아 |
| 5~15 | 빈 자리 (88KB) | |

ASCII8 은 0x6000/0x6800/0x7000/0x7800 에 뱅크 번호를 쓰면 해당 8KB 창이 바뀝니다. ROM 이라 쓰기는 흘러가고 매퍼만 값을 받습니다.

**켤 때 0x4000-0x5FFF 는 건드리지 않습니다.** 지금 실행 중인 코드가 거기 있어서, 다른 뱅크로 바꾸면 그 순간 코드가 사라집니다.

`SelectPage2`(PPI 슬롯 전환)는 그대로 필요합니다. 매퍼와 별개로, BIOS 가 카트리지를 페이지 1 에만 넣어 주는 것은 변하지 않기 때문입니다.

> **빌드가 세 번 돕니다.** 뱅크 3 과 4 가 둘 다 0xA000 에 놓여 한 번에 어셈블할 수 없습니다. `src/quest.asm`(본체), `src/questspr0.asm`, `src/questspr1.asm` 을 따로 어셈블하고 `build_quest.ps1` 이 이어 붙여 128KB 로 만듭니다.

> **openMSX 는 `-romtype` 을 `-cart` 뒤에서만 받습니다.** 앞에 두면 그냥 종료 코드 1 로 끝납니다. 찾는 데 시간이 걸렸습니다.

## 오른쪽 창 스크롤 - VDP 명령을 쓴다

전투 기록은 늘 맨 아래에 찍고 그 전에 한 줄 올립니다. 소프트웨어로 옮기면 13줄 x 54바이트를 VDP 로 읽고 쓰느라 한 줄에 90ms 가 걸려서, 한 라운드에 1초가 넘습니다.

V9938 의 명령 엔진을 씁니다. **HMMM**(VRAM 안에서 사각형 옮기기)로 한 줄 올리고 **HMMV**(사각형 채우기)로 맨 아래를 비웁니다.

```asm
    ld a, 32
    ld (CmdFirst), a
    ld hl, CmdScroll
    ld b, 15
    call SendVdpCmd
```

R#17 에 시작 레지스터 번호를 넣고 포트 0x9B 로 쏟아부으면 레지스터가 자동으로 올라갑니다. R#32~46 을 하나씩 쓰는 것보다 훨씬 짧습니다.

> **덫**: 명령이 끝났는지 보려면 상태 레지스터 S#2 를 읽어야 하는데, 그러려면 R#15 를 2 로 둬야 합니다. **읽고 나서 반드시 0 으로 되돌려야** 합니다. 안 그러면 다음에 VRAM 주소를 잡을 때 엉뚱한 상태 레지스터를 보게 됩니다.

## 곱셈과 나눗셈

Grauw 의 <https://map.grauw.nl/articles/mult_div_shifts.php> 를 옮겨 `src/questmath.asm` 에 넣었습니다. **`doc/z80_mult_div.md`** 에 왜 그 형태인지, 어디에 쓰고 어디에 일부러 안 썼는지 정리했습니다.

- `Div16` — 주사위의 편향 없애기(16 비트 난수 나머지). 매 주사위마다 돕니다.
- `Mult8` — 표 색인(직업 x22, 종족 x14, 몬스터 x20). 손으로 짠 시프트 사슬은 빠르지만 간격이 바뀌면 조용히 틀려서, 뜨겁지 않은 이 자리는 곱셈으로 바꿨습니다.
- **표** — 능력치 보정과 BAB. 나누는 수가 고정이고 범위가 좁으면 표가 압도적입니다.
- **일부러 안 바꾼 곳** — `PutNumR` 의 자릿수 만들기. 세 자리라 최대 스물일곱 번이고 이미 화면으로 확인해 둔 코드입니다.

## 32KB ROM 은 페이지 2 를 직접 잡아야 한다

텍스처를 넣으면서 데이터가 처음으로 0x8000 을 넘었더니 화면이 배경색 하나로만 나왔습니다. 원인은 매퍼가 아니라 **슬롯 선택** 이었습니다.

MSX BIOS 는 0x4000 의 "AB" 헤더를 보고 카트리지를 찾은 뒤 **그 슬롯을 페이지 1 에만** 넣어 줍니다. 페이지 2 는 여전히 RAM 이라 0x8000 위쪽이 전부 0xFF 로 읽혔고, 배경 압축 해제 루프가 데이터 끝을 못 만나 무한 루프에 빠졌습니다(에뮬레이터에서 PC 를 읽어 확인).

32KB ROM 은 자기 슬롯을 페이지 2 에도 직접 넣어야 합니다. PPI 포트 0xA8 의 페이지 1 슬롯 번호를 그대로 페이지 2 자리에 복사하면 됩니다 (`SelectPage2`). 이 코드는 기본 슬롯만 다루며, 확장 슬롯에 꽂힌 경우 서브슬롯까지 맞춰야 합니다.

> openMSX 는 이 ROM 을 `Mirrored` 로 자동 판정합니다(뒤쪽이 대부분 0 이라 16KB 로 봄). 하지만 `-romtype` 을 무엇으로 바꿔도 증상은 그대로였습니다 — 매퍼가 아니라 슬롯 문제였기 때문입니다.

## 렌더러

그려야 할 때만 그립니다. 이동도 회전도 없으면 메인 루프는 키만 봅니다.

뷰포트 96×96을 "각 픽셀이 어느 면에 속하는가"로 미리 구워, 스캔라인마다 `(면번호, 바이트폭)` 런으로 만들어 두었습니다(1,328바이트, 한 줄 최대 11런). 실행 중에는

1. 지도를 한 번 보고 면 번호별 색을 정하고 (`BuildColours`)
2. 런을 따라가며 그 색으로 칠합니다 (`RenderDungeon`)

안쪽 루프에 지도 조회가 없습니다.

**줄마다 VRAM 주소를 딱 한 번만 잡습니다.** VDP 주소는 자동으로 증가하므로 런과 런 사이에 다시 잡을 필요가 없습니다. 처음에는 면 단위로 칠했는데, 한 줄에 주소를 네댓 번씩 잡느라 전체의 상당 부분을 주소 설정에 썼습니다.

앞이 막혔을 때 그보다 깊은 면들을 **빼고 그리는 것이 아니라 전부 정면 벽 색으로 칠합니다.** 막힌 칸의 정면 사각형은 그보다 깊은 면들과 한가운데를 정확히 덮으므로 결과가 같고, 기하 구조를 위치와 무관한 고정 표로 남길 수 있습니다.

## 속도 (실측)

에뮬레이터에 중단점을 걸어 `RenderDungeon` 진입부터 메인 루프 복귀까지를 쟀습니다.

| 단계 | 한 번 다시 그리는 시간 |
|---|---|
| 면 단위로 칠하던 처음 방식 | 98 ms (5.9 프레임) |
| 스캔라인 런 방식 | 62 ms (3.7 프레임) |
| 내가 선 칸까지 그리도록 확장 | 69 ms (4.2 프레임) |
| VRAM 쓰기 간격을 29 T-state 로 정확히 맞춤 | 73 ms (4.4 프레임) |
| **벽돌 텍스처 도입** — 안쪽 루프가 RAM 변수를 쓰던 첫 판 | 110 ms (6.6 프레임) |
| **안쪽 루프를 레지스터만 쓰도록 정리** | 82 ms (통로) / 102 ms (막다른 곳) |
| 줄눈을 가늘게 + 옆길에 뚫린 그림 추가 (블록 2개) | 95 ms / 116 ms |
| 핫 패스의 call 을 인라인 | **92 ms (통로) / 109 ms (막다른 곳)** |
| 옆길을 "벽이 없었다면 보였을 그림" 으로 다시 구움 | 92 ms / 109 ms (그대로 - 굽는 내용만 바뀜) |
| 바닥/천장에 상자 필터 | 92 ms / 109 ms (그대로 - 굽는 시점에 끝난다) |

이론상 하한은 4,608바이트 × 30 T-state = 39 ms 입니다. VRAM에 쓰는 것 자체가 그만큼 걸립니다.

텍스처를 넣으면서 처음에는 110 ms 로 뛰었는데, 원인은 그림이 아니라 **안쪽 루프가 런마다 RAM 변수를 대여섯 번 읽고 쓴 것** 이었습니다. `ld a,(nn)` 하나가 13 T-state 인데 런이 570 개쯤 되니 그것만 180k T 였습니다. HL·B·C·D 를 고정 배치로 잡아 레지스터만 쓰도록 정리해 런당 250 T → 80 T 로 줄였습니다.

막다른 곳이 20 ms 더 드는 것은 정면 벽을 2단계에서 따로 붙이기 때문입니다.

마지막 줄에서 3 ms 가 늘어난 것은 일부러입니다. 화면이 켜져 있는 동안 V9938 은 VRAM 쓰기 간격을 **29 T-state 이상** 요구하는데, `out + nop + djnz` 는 28 이라 1 이 모자랍니다. 에뮬레이터에서는 문제없이 보였지만 실기에서는 쓰기가 누락될 수 있어, `djnz` 를 `dec b + jp nz` 로 바꿔 정확히 29 를 맞췄습니다.

한 걸음에 0.07초이므로 키를 누르면 바로 반응하는 느낌입니다.

## 겪은 버그 — 서브루틴이 BC를 뭉갬

측벽이 전부 검게 나오는 증상이 있었습니다. 원인은 `IsWall`이 주소 계산에 `ld bc, MapData`를 쓰면서 **BC를 파괴**했는데, 부르는 쪽은 B에 구간 번호를 들고 있었던 것입니다. 돌아온 뒤 B로 색과 면 번호를 계산하니 엉뚱한 슬롯에 색이 들어가고, 진짜 좌우 벽 슬롯은 0(검정)으로 남았습니다.

같은 이유로 `CellAhead`와 `NeighbourCell`도 BC를 보존하도록 고쳤습니다. 지금은 지도 관련 루틴이 전부 BC를 보존합니다.

같은 작업 중에 **후진할 때 방향이 틀어지는 버그**도 찾았습니다. 뒤 칸을 계산하려고 방향을 잠깐 뒤집는데, 원래 방향을 B에 담아 두었더니 `CellAhead`가 그 B를 파괴했습니다. 지금은 스택에 넣습니다.

> 이 프로젝트에서 같은 유형(루프가 들고 있는 레지스터를 서브루틴이 파괴)을 세 번째 겪었습니다. 인덱스를 레지스터에 담고 배열을 훑는 루프 안에서 서브루틴을 부를 때는 그 루틴의 레지스터 파괴 목록을 반드시 확인해야 합니다.

## 검증 방법

`gfx/quest_preview.py` 가 **`quest.asm` 의 렌더러를 그대로 옮겨** 놓았습니다. 면 상태를 정하는 규칙(`BuildVisibility`)도, 그 상태로 픽셀을 고르는 규칙(이중 블록 처리)도 같고, 픽셀 자체도 ROM 에 들어가는 것과 같은 굽기 함수에서 가져옵니다. 다른 점은 16색으로 줄이지 않는다는 것 하나뿐입니다.

`gfx/quest_diff.py` 가 둘을 픽셀 단위로 비교합니다. 미리보기를 변환기와 똑같은 규칙으로 팔레트에 맞춘 뒤, openMSX 가 화면에 내보내는 값으로 바꿔 에뮬레이터 화면과 겹칩니다.

```powershell
uv run --with pillow python gfx\quest_diff.py <스크린샷 폴더>
```

현재 결과는 **화면당 0.1~0.25%** 이고, 다른 자리도 정해져 있습니다. `build_runs` 가 두 픽셀을 한 바이트에 담기 때문에 런 경계가 바이트 한가운데 걸리면 그 바이트가 한쪽 면의 색으로 통일되는데, 미리보기는 픽셀 단위라 거기서만 갈립니다. **그보다 큰 차이가 나오면 진짜 회귀입니다.**

> openMSX 는 V9938 의 3비트 채널을 `0 43 81 118 153 187 221 255` 로 내보냅니다. 선형(`v*255/7`)이 아니라서, 이 표를 안 쓰면 멀쩡한 화면도 85% 가 다르다고 나옵니다.

이동 검증은 `verify_quest.ps1 -Keys` 로 키를 넣어 좌표와 방향을 메모리에서 직접 읽어 확인했습니다. 전진·회전·벽에 막힘이 모두 지도와 일치합니다.

## ROM 사용량

128KB 중 **40,960바이트**(뱅크 0~4)를 씁니다. 본체가 23,256 / 24,576, 몬스터 그림이 8,338 입니다. 매퍼는 필요 없지만 페이지 2 슬롯 전환은 필요합니다(위 절 참고).

**본체 여유가 1,320 바이트뿐입니다.** 여기가 다음 병목입니다. 더 넣으려면 배경 RLE(6,438 바이트, 부팅 때 한 번만 읽음)를 뱅크로 빼면 됩니다 — 읽고 버리는 자료라 옮기기 쉽습니다.

뱅크 5~15 는 비어 있습니다(88KB). 그림과 층 자료를 넣을 자리는 넉넉합니다.
