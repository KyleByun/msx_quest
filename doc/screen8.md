# SCREEN 8 로 옮기기

> **결론부터**: 옮겼다. `build/quest3.rom` 이 SCREEN 8 판이고 `src/quest3.asm` 이 지금 쓰는 소스다. `src/quest.asm` (SCREEN 5) 은 보관용으로 얼려 두었다 — 다만 `verify_quest_sides.ps1` 의 **픽셀 단위 오라클이 4bpp 에서만 돌기** 때문에, 공유하는 하위 파일을 고쳤을 때는 그쪽도 빌드해서 검사를 돌린다.
>
> | | SCREEN 5 | SCREEN 8 |
> |---|---|---|
> | 던전 한 장 (plaza) | 105.9 ms | 149.6 ms |
> | 던전 한 장 (코앞이 벽) | 95.1 ms | 131.9 ms |
> | 몬스터 | 64x64, 여섯 마리가 16색을 나눠 씀 | **96x96, 45색** |
> | 롬 사용 | 9 뱅크 (73,728 B) | 14 뱅크 (114,688 B) |

아래는 옮기기 전에 **재 본 것**이다. `quest.rom` 은 SCREEN 5(GRAPHIC 4)로 되어 있었고, SCREEN 8(GRAPHIC 7)로 옮기면 색이 16 에서 256 으로 는다. 옮길 만한 일인지 알아보려고 **타진용 롬**을 따로 만들었다.

```
build_questprobe.ps1     src/questprobe.asm -> build/questprobe.rom (16KB, 매퍼 없음)
verify_questprobe.ps1    openMSX 로 돌려서 재고, 표로 낸다
gfx/questprobe.py  Tcl 생성 + 결과 판정 + 팔레트 -> GRB332 변환
```

`quest.rom` 과 아무것도 나눠 쓰지 않는다. 게임을 옮긴 것이 **아니라** 옮기기 전에 알아야 할 것만 재는 롬이다.

## 왜 롬을 따로 만들었나

두 모드의 차이 대부분은 종이에서 다 나온다.

| | SCREEN 5 (G4) | SCREEN 8 (G7) |
|---|---|---|
| 한 바이트 | 픽셀 둘 (4bpp) | 픽셀 하나 (8bpp) |
| VRAM 주소 | `y*128 + x/2` | `y*256 + x` |
| 색 | 팔레트 16색 (RGB333) | 팔레트 없음. GRB332 고정 256색 |
| 한 화면 | 27,136 바이트 | 54,272 바이트 |

주소 계산은 **오히려 짧아진다** — `srl h` / `rr l` 이 통째로 없어지고 `ld h, y` / `ld l, x` 면 끝이다. 자료가 두 배가 되는 것도 계산으로 나온다.

**종이에서 안 나오는 것은 대역폭 하나뿐이다.** GRAPHIC 6/7 은 VDP 가 한 줄에 두 배를 읽어 가서, 화면을 켠 채로는 CPU 가 VRAM 을 만질 틈이 줄어든다고 알려져 있다. 그 최소 간격이 8 us 냐 15 us 냐에 따라 던전 한 장이 두 배 느려지느냐 네 배 느려지느냐가 갈리고, 그러면 결론 자체가 갈린다. 그래서 **외워 쓰지 않고 쟀다.**

## 잰 것 1 — 간격과 시간

`outi` 뒤에 넣는 `nop` 수를 일곱 가지로 두고 96×96 을 각각 그린다. 시간은 롬 안에서 재지 않는다. `BlitStart` / `BlitEnd` 에 브레이크포인트를 걸고 `machine_info time` 을 뺀다.

```
변형  안쪽 고리          T/바이트    us     96x96     프레임  흘림  VDP경고
  0   outi+jp             29.0 T    8.1     84.4 ms    5.1      0        0
  1   outi+nop+jp         34.0 T    9.5     97.3 ms    5.8      0        0
  2   outi+3nop           44.0 T   12.3    123.0 ms    7.4      0        0
  3   outi+6nop           59.0 T   16.5    161.6 ms    9.7      0        0
  4   outi+10nop          79.0 T   22.1    213.1 ms   12.8      0        0
  5   outi+16nop         109.0 T   30.5    290.4 ms   17.4      0        0
  6   outi x8 (대조군)     19.4 T    5.4     59.6 ms    3.6      0        0
```

T 는 **MSX 의 M1 대기까지 넣은 값**이다. 명령어를 읽을 때마다 1 T 씩 더 드니 `outi` 는 ED 접두라 16+2, `nop` 은 4+1, `jp` 는 10+1 이다. 처음에는 이것을 빼먹고 계산했다가 클록이 2.86MHz 라는 말이 안 되는 값이 나왔다. M1 대기를 넣으면 변형 사이의 기울기가 정확히 3.579MHz 로 떨어지고, 변형 0 의 절대값도 계산과 **0.4% 안에서** 맞는다. 이 숫자들은 믿어도 된다.

## 잰 것 2 — 그 숫자가 뜻이 있는가 (카나리아)

"흘림 0" 은 두 가지로 읽힌다. **정말 안 흘린 것**이거나 **에뮬레이터가 그 고장을 안 흉내내는 것**이거나. 구별하지 않으면 아무 말도 한 것이 없다.

그래서 확실히 너무 빠른 접근을 넷 만들어 두었다. `out (n),a` 는 12 T(3.35 us)로 `outi` 보다도 짧아서 어떤 화면 모드에서도 규격 밖이다.

```
카나리아 (out (n),a = 12 T = 3.35 us)
   쓰기 G7 0, 쓰기 G4 0, 읽기 G7 0, 명령 엔진 도는 중 쓰기 0   (콜백 = tfva)
```

**넷 다 한 번도 안 걸렸다.** openMSX 21.0 에는 `too_fast_vram_access` 설정(기본 `real`)과 `VDP.too_fast_vram_access_callback` 이 있고 콜백은 제대로 붙었지만(값이 `tfva` 로 남아 있다), 화면 표시와의 VRAM 다툼은 흉내내지 않는다.

> 그러므로 위 표의 **'흘림' 칸은 최소 간격의 근거가 못 된다.** 실기에서 확인해야 한다.
> **'걸린 시간' 칸은 그대로 쓸 수 있다** — 그쪽은 T-state 계산과 맞는다.

이것을 못 박아 두는 이유가 있다. 이 프로젝트에서 "확인했다"고 적어 놓은 것이 실제로는 확인이 아니었던 적이 두 번 있었다(`random_map.md` 참고). 통과한 검사도 **왜** 통과했는지 알아야 한다.

## 잰 것 3 — 명령 엔진 좌표

양피지 창(`MsgClear` / `MsgScroll` / `MenuClear`)은 전부 HMMV/HMMM 이다. GRAPHIC 4 에서는 CLR 한 바이트가 픽셀 **둘**이라 `COL_CREAM * 17` 로 써 왔는데, GRAPHIC 7 에서는 어떻게 되는가.

```
HMMV  x=136..151 딱 그만큼 칠해졌다 - 좌표는 픽셀 단위, CLR 한 바이트 = 한 픽셀  OK
HMMM  x=136..151 딱 그만큼 칠해졌다 - 좌표는 픽셀 단위, CLR 한 바이트 = 한 픽셀  OK
```

**좌표는 그대로 두면 된다.** `MSG_X = 136` 같은 값을 고칠 필요가 없다. 고칠 것은 CLR 바이트뿐 — `COL_CREAM * 17` 이 아니라 그 색의 GRB332 값 하나가 된다.

## 잰 것 4 — 색

SCREEN 8 에는 팔레트가 없다. 색이 GRB332 로 못박혀 있다(bit7-5 = G, bit4-2 = R, bit1-0 = B). R 과 G 는 3 비트가 그대로 가고 **파랑만 8 단계에서 4 단계로 준다.**

```
팔레트 16색 -> GRB332 에서 13 가지로 남는다
   0xB5 에서 겹침: 5(5,5,3), 15(5,5,2)
   0xDE 에서 겹침: 2(7,6,5), 13(7,6,4)
   0xFF 에서 겹침: 0(7,7,6), 12(7,7,7)
```

**크림(0)과 흰색(12)이 같은 색이 된다.** 지금 값을 그대로 옮기면 양피지와 벽면 하이라이트의 대비가 사라진다.

다만 이건 **막는 것이 아니라 오히려 짐이 덜어지는 쪽**이다. SCREEN 8 에서는 애초에 "16 자리를 무엇으로 채울까"를 고를 일이 없다 — 픽셀마다 GRB332 바이트를 아무거나 쓰면 된다. `quest_pal.nearest` 도 `RESERVED` 도 할 일이 없어지고, 미니맵의 파랑(`COL_HERO`)은 그냥 원하는 파랑을 쓰면 된다. 배경 그림도 16색으로 줄일 이유가 없어진다.

겹침 표가 말해 주는 것은 "지금 고른 16색을 글자 그대로 옮기지 말라"는 것뿐이다.

롬 아래쪽에 16색 견본과 256색 전부를 나란히 찍어 두었다. 눈으로 볼 수 있다.

## 옮기면 얼마나 느려지나

`RenderDungeon` 을 같은 방법으로 잰다. **지도를 못박고** 잰다 — `verify_quest_sides.ps1` 이 쓰는 지도를 그대로 가져온다.

```
plaza     105.9 ms (6.4 프레임)     5x5 방 한가운데, 앞이 안 막힘
far2      100.6 ms (6.0 프레임)     멀리 벽이 있음
branch     99.1 ms (5.9 프레임)     좁은 통로
```

처음에는 부팅한 그대로 세 장을 재서 **가장 짧은 것**을 썼는데, 그건 층이 부팅마다 달라지는 값의 최솟값일 뿐이다. `RenderDungeon` 은 앞이 가까이 막히면 가운데를 통째로 건너뛰므로(`VIS_SKIP`) 서 있는 자리에 따라 옮기는 바이트가 다르다. 가장 싼 화면을 기준으로 삼으면 어림이 낙관적으로 기운다. 지금은 지도를 정해 두고 재고, **가장 무거운 화면**에 얹는다.

늘어나는 것은 **픽셀 옮기는 양뿐**이다. 가시성 계산도 런 해독도 그대로다. 4,608 → 9,216 바이트니 4,608 바이트 값어치만 더 든다.

| VRAM 간격 | 더 드는 시간 | 던전 한 장 (plaza 기준) |
|---|---|---|
| 9.5 us (지금 쓰는 간격) | +43.8 ms | 150 ms (9.0 프레임) |
| 16.5 us | +76.0 ms | 182 ms (10.9 프레임) |
| 22.1 us | +101.7 ms | 208 ms (12.5 프레임) |

칸 단위로 움직이는 게임이라 한 걸음에 0.15~0.2 초는 견딜 만하다. **속도가 막는 것은 아니다.** 다만 간격이 얼마인지는 실기에서 확인해야 한다.

## 옮기려면 진짜로 해야 하는 일

속도가 아니라 **자리**가 문제다. 다만 여기서 말하는 자리는 **롬 전체가 아니라 한 번에 보이는 창**이다.

| | 지금 | SCREEN 8 |
|---|---|---|
| 벽면 런 (`RunData`) | 12,117 바이트 | 약 24,200 |
| 정면 벽 (`Front*`) | 3,808 | 약 7,600 |
| 배경 RLE | 6,344 | 1~2 뱅크 |
| 몬스터 그림 | 8,338 | 약 16,700 |
| 본체(뱅크 0~2) 남은 자리 | **1,443 바이트** | |
| **롬 전체 남은 자리** | **80KB (10 뱅크)** | |

ASCII8 은 8KB 창 넷이다. 0x4000-0x9FFF 세 창은 뱅크 0~2 로 **고정**해 두었고 0xA000 창만 갈아 끼운다. 벽면 자료가 지금 이 고정 구역에 있어서 꽉 찬 것이지, **롬이 모자란 것이 아니다.** 128KB 중 80KB 가 비어 있다.

### 방법 하나 — 벽면 자료를 0xA000 창으로 내린다

`RenderDungeon` 이 런 자료를 읽는 방식이 마침 이것에 딱 맞는다. `HL` 이 `RunData` 부터 **한 번, 앞으로만** 훑는다. 되돌아가지도 건너뛰어 되짚지도 않는다 — 전진은 전부 `add a, l / ld l, a / jp nc / inc h` 다.

그래서 뱅크 경계 검사를 **줄머리에 한 번**만 두면 된다. 생성기가 한 줄치 자료를 뱅크에 걸치지 않게 채워 넣으면(뱅크 끝에 남는 자투리는 버린다, 3% 남짓) 다음이 전부다.

```asm
.line:
    ld a, h
    cp 0xC0                     ; 창을 넘었나
    jr c, .ok
    ld hl, WallBank             ; 다음 뱅크로 갈아 끼우고 창 앞으로
    inc (hl)
    ld a, (hl)
    ld (ASC8_P3), a
    ld hl, 0xA000
.ok:
```

96 줄 x 약 20 T = **0.5 ms**. 잰 값(100 ms)에 비하면 없는 것과 같다. 정면 벽(`Front*`)은 깊이로 골라 읽는 자료라 (뱅크, 주소) 표를 고정 구역에 두면 되고, 그리는 시점이 런 훑기 뒤라 창을 다시 걸어도 상관없다.

몬스터 그림이 이미 같은 창을 이렇게 쓰고 있다(뱅크 3/4). 새로 발명할 것이 없다.

### 방법 둘 — 벽면을 아예 VRAM 에 굽는다

SCREEN 8 은 페이지 0 이 64KB 라 VRAM 128KB 중 **64KB 가 남는다.** 부팅할 때 벽면 픽셀을 그 자리에 풀어 두고, 그릴 때는 VDP 에게 오려 붙이라고(HMMM) 시키는 방법이다. 그러면 벽면 자료가 롬의 실행 경로에서 통째로 빠진다.

재 봤다.

```
같은 넓이(96x96 = 9,216 픽셀)
   HMMM (VRAM 안에서 복사)   42.0 ms      Z80 이 미는 것보다 1.4 배 빠르다
   HMMV (단색 채우기)        25.5 ms      2.3 배 빠르다
   (Z80 이 제일 빠른 간격으로 밀었을 때가 59.6 ms)
```

**픽셀만 놓고 보면 VDP 가 빠르다.** 그런데 한 장에 런이 **664 개**다(세 지도 모두 같다 — 런 구조가 정해져 있다). 런마다 명령 하나씩이면 준비 시간만 664 x 약 0.15 ms = 96 ms 라, 합쳐서 138 ms. Z80 으로 미는 150 ms 와 별 차이가 없다.

> 명령 하나에 드는 0.15 ms 는 **계산한 값**이다(`WaitVdpCmd` + R#17 쓰기 + `otir` 15 바이트 ≈ 520 T). 재지는 않았다.

그러니 이 방법은 **속도로는 남는 것이 없고, 롬 자리로는 크게 남는다.** 그리고 넓고 평평한 자리(통로 끝의 어둠, 정면 벽 한 덩어리)에는 명령이 몇 개뿐이라 확실히 이득이다 — **섞어 쓰는 것**이 맞다.

### 128KB 보다 큰 롬은 되는가

된다. ASCII8 의 뱅크 번호는 8 비트라 **256 뱅크 x 8KB = 2MB** 까지 간다. 다만 **지금은 그럴 필요가 없다.** 벽면(32KB) + 배경(2뱅크) + 몬스터(3뱅크) + 본체(3뱅크)를 다 더해도 13 뱅크(104KB)로, 128KB 안에 들어간다.

RAM 이 많은 기계(메모리 매퍼)는 **도움이 안 된다.** 롬을 읽는 속도나 RAM 을 읽는 속도나 같고, RAM 도 결국 같은 창으로 갈아 끼워야 한다. 자료를 RAM 에 옮겨 놓는 값어치가 없다.

### 그 밖에 손볼 곳(전부 기계적이다)

- VDP 레지스터 표 R#0 `0x06` → `0x0E`. R#1, R#2, R#8, R#9 는 그대로.
- 팔레트 올리기(`UploadPalette`)가 통째로 없어진다.
- VRAM 주소 계산이 짧아진다 (`srl h` / `rr l` 삭제).
- 글자 펼치기 표가 니블→2바이트에서 니블→4바이트로 (32 → 64 바이트).
- `BLACK_BYTE`, `MINIMAP_*_BYTE`, HMMV 의 CLR 이 "같은 색 두 픽셀"에서 한 픽셀로.
- `gfx/quest_convert.py` 의 `(hi << 4) | lo` 다섯 자리를 두 바이트 넣기로.
- **모드를 오가면 VRAM 배치가 어긋난다.** G6/G7 은 VRAM 두 칩에 번갈아 담아서, G7→G4→G7 을 하면 화면이 통째로 밀린다. 타진 롬을 만들다 실제로 겪었다(덤프가 두 칸씩 밀려 나왔다). 게임에서는 모드를 안 바꾸므로 상관없지만, 알고는 있어야 한다.


## 옮기고 나서 - 실제로 걸린 것들

### 벽면은 256색으로 가도 안 나아진다

옮기기 전에 재 본 것 중 이게 제일 뜻밖이었다.

| | 구운 원본 | 16색으로 | GRB332 로 |
|---|---|---|---|
| 벽면 | 173가지 | 7가지 | **8가지** |
| 몬스터 | 63가지 | 14가지 | **45가지** |

벽돌 텍스처가 **회색조**라서다. GRB332 는 R·G 가 3비트인데 B 가 2비트뿐이라 진짜 회색은 8단계밖에 안 나온다. 지금 팔레트가 회색에 7칸을 쓰고 있으니 한 칸 늘어나는 것이 전부인데, 자료는 12KB 에서 23KB 로 두 배가 된다.

병목이 팔레트가 아니라 `quest_tex.py` 가 회색 벽돌만 굽고 있다는 것이다. 256색을 살리려면 텍스처에 색을 넣어야 하는데(따뜻한 사암, 이끼, 횃불빛) 그건 형식 문제가 아니라 그림을 어떻게 할지의 문제라 일부러 안 건드렸다.

반면 몬스터는 3배다. 게다가 지금까지 여섯 마리가 16칸을 **나눠 쓰고** 있었다 - 몬스터에 파란 점이 박히던 그 문제가 여기서 나온 것이다.

### 픽셀 단위 오라클을 잃지 않으려고 순서를 지켰다

`verify_quest_sides.ps1` 은 던전 화면을 파이썬 모델과 **픽셀 하나까지** 맞춰 본다. 그 모델이 4bpp 기준이라 8bpp 에서는 안 돈다. 그래서 큰 구조 변경을 전부 **SCREEN 5 에서 먼저** 하고 그 검사로 잠근 뒤에 모드를 바꿨다.

1. 정면 벽 -> VRAM + HMMM   (7개 지도 픽셀 0 차이)
2. 벽면 런 -> 뱅크          (7개 지도 픽셀 0 차이)
3. 그다음에 8bpp

8bpp 에서 같은 버그가 나면 대조할 기준이 없다. 순서를 반대로 했으면 어디가 깨졌는지 알 수가 없었을 것이다.

### 눈으로 보다가 잡은 것 둘

8bpp 에는 오라클이 없어서 결국 화면을 보고 잡았다.

1. **미니맵 한 칸이 3바이트로 박혀 있었다.** 8bpp 는 6바이트라 지도가 줄무늬로 나왔다. `MINIMAP_CELL / PXB` 로 고쳤다.
2. **`RowAddrB` 가 `ld d, 0` 으로 D 를 뭉갰다.** `DrawMap` 이 D 에 화면 y 를 들고 부르는데. 이 프로젝트에서 레지스터 뭉갠 버그 일곱 번째다 - 이번에도 "공통 루틴으로 묶으면서 원래 없던 레지스터 사용이 생긴" 꼴이었다.

### 모드를 오가면 VRAM 이 어긋난다

G6/G7 은 VRAM 두 칩에 **번갈아** 담는다. G7 -> G4 -> G7 을 하면 화면이 통째로 밀린다. 타진 롬에서 카나리아를 G4 로도 돌려 보려다 덤프가 두 칸씩 밀려 나와서 알았다. 게임에서는 모드를 안 바꾸니 상관없지만, 타진 롬은 카나리아를 **덤프 뒤로** 미뤄야 했다.

### 17 비트 VRAM 주소

정면 벽을 놓는 줄 256 이 SCREEN 8 에서는 VRAM 0x10000 이다. `SetVramWrite` 는 16 비트만 받으므로 R#14 의 A16 비트를 얹는 `SetVramWriteFront` 를 따로 두었다. SCREEN 5 에서는 같은 자리가 0x8000 이라 16 비트에 들어간다.

### 화면 밖 VRAM 은 `FRONT_PIX_LEN / VRAM_ROW` 줄이 아니다

정면 벽 픽셀은 **깊이별 사각형을 세로로 쌓아** 둔다(`UnpackFront` 가 줄마다 `VRAM_ROW` 씩 건너뛴다). 폭은 제일 넓은 깊이 1 이 72 바이트뿐이라 줄마다 오른쪽이 남는다.

| | 줄 | 크기 |
|---|---|---|
| 깊이 1 | 256~328 | 72 x 73 |
| 깊이 2 | 329~365 | 36 x 37 |
| 깊이 3 | 366~390 | 24 x 25 |
| 깊이 4 | 391~409 | 20 x 19 |

합이 7,568 바이트(`FRONT_PIX_LEN`)지만 차지하는 줄은 **154 줄**이다. 한 줄 256 바이트로 나눈 30 줄이 아니다.

`questmonrow.asm` 이 이 나눗셈으로 정면 벽의 끝을 재고 그 뒤(줄 300, 310)에 화살표 띠와 칼질 칸을 놓았다. 실제로는 정면 벽 **위**였다. 증상은 전투를 한 번 하고 나서 막다른 길에 서면 벽에 그때 떠 둔 몬스터가 박혀 보이는 것이었고, 다시 그려도 그대로였다 — 그리기가 빠뜨린 것이 아니라 HMMM 으로 오려 붙일 원본이 망가진 것이라서.

지금은 줄이 아니라 **x 로 피한다.** `SCRATCH_X equ 128` 로 정면 벽 그림(x 0~71) 오른쪽에 놓고, 생성기가 `FRONT_ROWS` / `FRONT_MAXW` / `FRONT_END_VY` 를 함께 구워 `ASSERT SCRATCH_X >= FRONT_MAXW` 로 막는다. 배치를 아는 것은 생성기뿐이니 경계값도 생성기가 내야 한다.

## 던전을 뒷면에 합성한다

던전도 몬스터도 화면이 아니라 BACK 에 그리고, 다 되면 HMMM 한 번으로 화면에 옮긴다(`ComposeView`). 그리는 과정이 안 보이는 것보다 더 큰 소득은 **지운 자리를 되살릴 밑그림이 늘 있다**는 것이다. 흔들기·떠오르는 숫자·칼질처럼 잠깐 덮었다가 되돌려야 하는 연출이 전부 "BACK 에서 오려 오기" 한 줄로 끝난다. 칼질이 쓰던 저장 영역은 그래서 없앴다.

**x 를 뷰포트와 같게 둔 것이 요령이다.** 그러면 화면에 그리던 코드를 한 줄도 안 고치고 줄만 옮겨서 그대로 뒷면에 그린다. CPU 로 VRAM 에 쓰는 길은 `RowAddr` + `SetVramWrite` 둘뿐이고 VDP 명령은 `DrawFront` 하나뿐이라, 그 셋에 `DrawYOfs` / `DrawA16` / `CmdYOfs` 를 얹는 것으로 끝났다.

값은 재 보니 이렇다.

```
던전 한 장 (화면에 바로)      150 ms
던전 한 장 (뒷면 + 옮기기)    184 ms      + 34 ms
```

CLEAN 사본은 **전투 중에만** 뜬다. 몬스터를 흔들려면 있던 자리를 지울 바탕이 필요한데, 걸어 다닐 때는 몬스터가 없어 BACK 이 곧 바탕이다.

### 흔드는 것은 화면에서 하면 안 된다

처음에는 지우고 어긋난 자리에 다시 찍었다. `DrawOneMon` 이 25 ms 라 그 사이 몬스터가 **없는** 화면이 보여서, 흔들리는 것이 아니라 깜빡이는 것으로 보였다. BACK 의 칸을 통째로 밀어 붙여 보기도 했는데(명령 둘, 27 ms) 칸 안의 벽까지 같이 밀려 벽돌이 어긋났다. 지금은 어긋난 그림을 작업대에서 먼저 짓고 다 된 것을 한 번에 얹는다 - 짓는 동안 화면에는 제자리 그림이 그대로 있다.
