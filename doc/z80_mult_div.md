# Z80 곱셈·나눗셈 — quest.rom 에서 쓰는 방법

출처: **Grauw, "Multiplication, division and shifts"** — <https://map.grauw.nl/articles/mult_div_shifts.php>

구현은 `src/questmath.asm` 에 있습니다. 이 문서는 왜 그 형태인지와, 이 프로젝트에서 **어디에 쓰고 어디에 일부러 안 썼는지**를 적습니다.

---

## Z80 에는 곱셈 명령이 없다

Z80 명령 집합에는 `MUL` 도 `DIV` 도 없습니다. 대신 이런 것들이 있습니다.

| 명령 | 하는 일 | T-state |
|---|---|---|
| `add a,a` | A 를 2 배 | 4 |
| `sla a` | 같은 일 | 8 |
| `add hl,hl` | HL 을 2 배 | 11 |
| `srl a` | A 를 2 로 나눔 (부호 없음) | 8 |
| `sra a` | A 를 2 로 나눔 (부호 있음, **내림**) | 8 |

**2의 거듭제곱은 시프트로 끝납니다.** `add a,a` 가 `sla a` 보다 두 배 빠르므로 왼쪽으로 밀 때는 `add a,a` 를 씁니다.

> 이 프로젝트에서 파티 기록의 간격을 32 로, 메시지 줄 간격을 8 로 잡은 것이 이 때문입니다. `사람번호 x 32` 가 `add hl,hl` 다섯 번으로 끝납니다.

## 곱셈 — 세로셈을 그대로

곱셈은 학교에서 배우는 세로셈과 같습니다. 곱하는 수의 비트를 위에서부터 하나씩 보면서, 결과를 두 배로 밀고 그 비트가 1 이면 곱해지는 수를 더합니다.

```asm
; H x E -> HL   (8 x 8 = 16 비트)
Mult8:
    ld d, 0
    ld l, d
    ld b, 8
.loop:
    add hl, hl          ; 결과를 두 배로 밀면서
    jr nc, .noadd       ; 밀려 나온 비트가 1 이면
    add hl, de          ; 곱해지는 수를 더한다
.noadd:
    djnz .loop
    ret
```

**핵심은 레지스터 하나로 두 몫을 하는 것입니다.** 처음에 H 에 곱하는 수를 두고 L 을 0 으로 둡니다. `add hl,hl` 로 밀면 H 의 최상위 비트가 캐리로 빠져나오고, 그 빈 자리를 아래에서 올라온 결과가 채웁니다. 여덟 번 돌면 곱하는 수는 전부 빠져나가고 HL 에는 결과만 남습니다. 곱하는 수를 따로 들고 다닐 필요가 없습니다.

```asm
; A x DE -> HL   (8 x 16, 넘치는 자리는 버린다)
Mult12:
    ld l, 0
    ld h, l
    ld b, 8
.loop:
    add hl, hl
    add a, a            ; 이쪽은 A 를 따로 민다
    jr nc, .noadd
    add hl, de
.noadd:
    djnz .loop
    ret
```

Grauw 는 펼친 판(`Mult12U`, 루프 없이 여덟 번을 그대로 나열)도 싣고 있습니다. **평균 268 T-state** (최소 235, 최대 301) 로 `djnz` 값을 아낍니다. 이 프로젝트는 곱셈이 뜨거운 자리에 없어서 짧은 쪽을 씁니다.

## 나눗셈 — 복원식 세로셈

나눗셈은 반대로 밀면서 빼 봅니다. 빼서 음수가 되면 되돌립니다(복원).

```asm
; E / C -> A 몫, B 나머지
Div8:
    xor a
    ld b, 8
.loop:
    rl e                ; 피제수를 한 비트 올리고
    rla                 ; 나머지에 받아
    sub c               ; 나누는 수를 빼 본다
    jr nc, .noadd
    add a, c            ; 음수면 되돌린다
.noadd:
    djnz .loop
    ld b, a
    ld a, e
    rla
    cpl                 ; 몫 비트가 뒤집혀 쌓이므로 마지막에 뒤집는다
    ret
```

**`cpl` 이 붙는 이유**가 처음에는 이상해 보입니다. `sub` 이 성공하면 캐리가 0, 실패하면 1 이 되는데, 그 캐리가 `rl e` 로 E 의 아래에서 밀려 들어가며 몫을 만듭니다. 즉 몫의 각 비트가 뒤집힌 채로 쌓입니다. 그래서 마지막에 한 번 뒤집으면 제대로 된 몫이 나옵니다.

16 비트 판(`Div16`)은 같은 것을 두 번에 나눠서 합니다. 상위 8 비트를 돌리고 그다음 하위 8 비트를 돌립니다.

## 상수로 나눌 때는 표가 더 낫다

일반 나눗셈은 16 단계를 돌지만, **나누는 수가 고정이고 범위가 좁으면 표가 압도적으로 빠릅니다.**

이 프로젝트에서 D&D 능력치 보정이 그 예입니다.

```python
# dice.py
def ability_modifier(score):
    return (score - 10) // 2
```

`//` 는 파이썬의 **내림** 나눗셈이라 8 이 -1, 7 이 -2 입니다. `sra a` 가 마침 내림이라 흉내 낼 수 있지만, 점수 범위가 0~31 뿐이라 **32 바이트짜리 표** 한 번 읽는 것이 더 빠르고 틀릴 일도 없습니다. `gfx/quest_rules.py` 가 파이썬 원본을 실제로 실행해서 그 표를 굽습니다.

같은 이유로 BAB 표도 굽습니다. `calc_base_attack_bonus` 의 `average` 가 `int(레벨*0.75)` 인데, 이것을 `레벨*3/4` 로 옮기면 반올림 방향 때문에 레벨 1 에서 1 이 나옵니다. 정답은 0 입니다.

> **규칙**: 나누는 수가 고정이고 피제수 범위가 좁으면 표. 실행 중에 둘 다 변하면 `Div8`.

Grauw 는 상수 나눗셈을 시프트와 덧셈으로 푸는 예도 싣고 있습니다. 예를 들어 9 로 나누기는 157 T-state 에 끝납니다(`Div16` 보다 훨씬 빠릅니다).

## 이 프로젝트에서 쓰는 곳

| 자리 | 방법 | 이유 |
|---|---|---|
| 사람 번호 x32, 메시지 줄 x8, 스프라이트 줄 주소 y x128 | `add hl,hl` 반복 | 2 의 거듭제곱이라 이게 최적 |
| 직업 표 x22, 종족 표 x14, 몬스터 표 x20 | **`Mult8`** | 2 의 거듭제곱이 아니다. 아래 참고 |
| 능력치 보정, BAB | **표** | 나누는 수 고정 + 좁은 범위 + 파이썬 내림 규칙 |
| 주사위 편향 없애기 | **`Div16`** | 16 비트 난수를 면 수로 나눈 나머지 |
| 자릿수 만들기 | 10 씩 빼기 | 세 자리뿐, 뜨겁지 않음 |

### 주사위에서 나눗셈이 왜 필요했나

8 비트 난수를 면 수로 나눈 나머지를 쓰면 `256 mod 20 = 16` 만큼 앞쪽 값이 자주 나옵니다. d20 에서 **6% 치우침**이라 전투에서 티가 납니다.

16 비트 난수를 나누면 `65536 mod 20 = 16` 이라 치우침이 **0.05%** 로 떨어집니다. 그래서 16 단계 나눗셈을 감수합니다. 한 번에 약 400 T-state 인데 주사위는 한 라운드에 스무 번 남짓이라 문제가 되지 않습니다.

## 일부러 안 바꾼 곳

`PutNumR` 과 `MsgAddNum` 의 자릿수 만들기는 10 을 빼면서 돕니다.

```asm
.div:
    cp 10
    jr c, .rem
    sub 10
    inc d
    jr .div
```

세 자리 숫자라 최대 스물일곱 번이고, 어차피 글자를 화면에 찍는 김에 도는 것이라 티가 나지 않습니다. **이미 화면으로 확인해 둔 코드를 빠르다는 이유만으로 건드리면 손해입니다.** `Div8` 로 바꾸면 16 단계가 고정으로 들어서 세 자리 이하에서는 오히려 느려질 수도 있습니다.

이 문서를 쓰면서 코드도 함께 손봤습니다.

| 자리 | 전 | 후 | 왜 |
|---|---|---|---|
| `RandMod` (주사위) | 손으로 짠 16 단계 복원식 `Mod16by8` | Grauw 의 **`Div16`** | 같은 알고리즘인데 출처가 분명한 쪽이 낫다 |
| `ClassPtr` (x22) | 손으로 짠 시프트 사슬 | **`Mult8`** | 간격이 바뀌면 사슬이 조용히 틀린다 |
| `RacePtr` (x14) | 시프트 사슬 | **`Mult8`** | 같음 |
| `MonTypePtr` (x20) | 시프트 사슬 | **`Mult8`** | 같음 |
| `PartyPtr` (x32) | `add hl,hl` 다섯 번 | 그대로 | 2 의 거듭제곱이라 이게 최적 |
| `PutNumR` 자릿수 | 10 씩 빼기 | 그대로 | 세 자리, 뜨겁지 않음, 이미 검증됨 |

시프트 사슬을 `Mult8` 로 바꾸면 표 하나 볼 때마다 약 400 T-state 를 더 씁니다. 한 라운드에 스무 번쯤 도니 8,000 T-state, 화면 한 프레임의 2% 입니다. **간격이 바뀌었을 때 조용히 틀리는 것보다 낫다고 보고 바꿨습니다.** 실제로 몬스터 표 간격이 이번에 17 에서 20 으로 늘었는데, 사슬이었다면 손으로 다시 짜야 했습니다.
