# 실행 시간 랜덤 맵 생성과 미니맵 (2026-08-31 작업)

이 문서는 quest.rom 에 **NetHack 식 랜덤 맵 생성**(`src/questlevel.asm`), **M키 미니맵**(`src/questmap.asm`)을 연결한 작업을 정리한다. 두 파일은 그 전까지 빌드에 포함되지 않은 WIP 였다.

## 무엇이 달라졌나

| 항목 | 이전 | 이후 |
|---|---|---|
| 맵 | `questdata.asm` 의 고정 16×16 (`MapData`) | 부팅마다 생성되는 `MapDataRam` (RAM 0xC2F4) |
| 시작 위치 | 고정 (1,13) | 첫 방의 중심 (생성 결과마다 다름) |
| 난수 시드 | 고정 0x1234 | RTC 시각 + Z80 R 레지스터 혼합 (`SeedRng`) |
| 지도 표시 | 없음 | M키 토글 미니맵 + 내 자리 방향 화살표 |
| 던전 뷰가 보는 맵 | ROM 고정 맵 | **미니맵과 같은 RAM 맵** (`IsWall` 전환) |

마지막 행이 중요하다. 한동안 미니맵은 RAM 의 생성 맵을 그리는데 렌더러는 ROM 의 고정 맵을 보고 있어서, **화면의 벽과 미니맵이 어긋나는** 증상이 있었다. `IsWall` 의 `ld bc, MapData` 를 `MapDataRam` 으로 바꿔 해결했다.

## 맵 생성 — NetHack 5.0 의 뼈대만

`D:\codes\NetHack-NetHack-5.0` 의 `src/mklev.c` 를 참고했다. 대응 관계:

| NetHack | quest.rom | note |
|---|---|---|
| `makelevel()` | `MakeLevel` | |
| `makerooms()` + `create_room()` | `PickRoom` / `CanPlaceRoom` / `CarveRoom` | 방 3~6개, 2~5×2~4, 32회 재시도 |
| `makecorridors()` 의 `join(i, i+1)` | `LinkRooms` | 새 방을 **직전 방과 항상** 연결 |
| `dig_corridor()` | `CarveH` / `CarveV` | **남은 거리가 먼 축부터** 파서 L자를 만든다 |

가져오지 않은 것: i,i+2 조인, 미연결 방 재조인, 여분(막힐 수 있는) 통로, 방 구조체/문/계단, 비밀통로. 16×16 소규모 맵에서는 "모든 방을 직전 방에 연결"만으로 NetHack 이 3단계에 걸쳐 보장하는 연결성과 같은 결론(항상 하나의 연결 성분)이 나온다.

### 통로가 방을 관통하지 않게 하는 NetHack 의 규칙

처음 `LinkRooms` 는 두 방 **중심**을 무작위 순서의 L자로 연결했다. 이러면 통로가 가는 길에 다른 방의 내부를 뚫고 지나갈 수 있다. NetHack 의 `dig_corridor()` 는 남은 거리 `dix`, `diy` 를 비교해 **먼 쪽 축부터** 파면서 굴곡을 만든다. 같은 규칙(`|dy| < |dx|` 이면 가로 먼저)을 이식해, 굴곡 위치가 기하로 결정되는 재현성 있는 L자로 바꿨다.

```
가로 먼저: (옛방중심x, 옛방중심y) → (새방중심x, 옛방중심y) → (새방중심x, 새방중심y)
세로 먼저: (옛방중심x, 옛방중심y) → (옛방중심x, 새방중심y) → (새방중심x, 새방중심y)
```

### 시드 — RTC + R 레지스터

`SeedRng` 은 MSX2 표준 RTC(RP-5C01, 포트 0xB4/0xB5)에서 초·분·시·일의 일의 자리 니블을 섞고 Z80 refresh register 까지 xor 한다. RTC 는 배터리로 돌아가므로 재부팅해도 같은 시드가 나오지 않는다. xorshift 는 0 을 시드로 못 쓰므로 0 이면 0xACE1 로 피한다.

C-BIOS_MSX2 에도 RTC 는 있다(hardwareconfig.xml 에 `<RTC>` 있음). openMSX 는 호스트 시계를 반영하므로 에뮬레이터에서도 부팅마다 다른 맵이 나온다.

### 연결성 — 손으로 두 번 본 것은 검증이 아니었다

처음에는 부팅 뒤 `MapDataRam` 을 덤프해 BFS 를 손으로 두 번 돌려 보고 "언제나 하나의 연결 성분"이라고 적었다. **그 상태로 지도 두 장 중 한 장꼴로 못 가는 방이 있었다.**

원인은 `LinkRooms` 의 가로-먼저 갈래다. `CarveV` 는 `A = 시작 y, B = x` 를 받는데, 주석에 그렇게 적어 놓고도 A 에 `RoomCX`(x)를, B 에 `PrevRoomY`(y)를 넣고 있었다.

```asm
    call CarveH
    ld a, (RoomCX)              ; A = x  (CarveV 는 A=시작y, B=x, C=끝y)  <- 인자를 뒤바꿈
    ld hl, PrevRoomY
    ld b, (hl)
```

그래서 L자의 두 번째 획이 **엉뚱한 열**(`x = PrevRoomY`)에 파이고, 새 방은 이어지지 않은 채로 남았다. 세로-먼저 갈래는 멀쩡했으므로 **절반은 정상으로 보였다** — 손으로 두 번 본 것이 둘 다 그 절반에 걸린 것이다.

증상 화면을 되읽어 보면 두 가지가 같이 보인다. 못 가는 방과, 아무 데도 닿지 않는 짧은 통로 한 줄. 그 통로의 열 번호가 직전 방 중심의 **y** 값과 같았던 것이 결정적인 단서였다.

### 이제는 한 번 부팅해서 48장을 본다

## 미니맵 — M키 토글

`questmap.asm`. 오른쪽 양피지 창(102×104) 안에 16×16 맵을 한 칸 6×6 픽셀로 확대해 그린다.

- 벽 = 회색, 통로 = 검정, 아직 안 가 본 칸 = 양피지 색, 내 자리 = 파란 방향 화살표
- 한 맵 행(48바이트)을 `MiniMapRow` 에 만들고 여섯 스캔라인에 반복 전송 — 4,608바이트 화면 버퍼가 필요 없다
- 전송은 `outi + nop + jp nz` = 30 T-state 로, 화면이 켜진 V9938 이 요구하는 29 이상을 지킨다
- 이동할 때마다 `AfterMove` → `DrawMap` 으로 현재 위치 표시가 따라간다

### 내 위치와 방향 - 한 자리에

처음에는 미니맵 **왼쪽 위에 나침반**을 따로 그렸다. 두 가지가 잘못이었다.

**하나, 제대로 그려지지 않았다.** `CompassPat` 은 방향별 패턴 주소가 2바이트씩 늘어선 표인데 `facing * 4` 로 짚고 있었다. 북쪽만 맞고, 동쪽은 남쪽 모양이 나오고, 남/서는 표 밖을 읽어 **엉뚱한 VRAM 주소에 낙서**를 했다. 화면 구석의 6×6 그림이라 한동안 눈치채지 못했다.

**둘, 자리가 잘못이었다.** 방향을 알려면 지도에서 눈을 떼 구석을 봐야 한다. 지금은 **내가 서 있는 칸에 바로 화살표**를 얹는다(`DrawHero`). "어디에 있고 어디를 보는가"가 한 번에 읽힌다.

화살표는 `MINIMAP_CELL` 그대로 6×6 이다. 이 크기에서는 모양 고르기가 실제로 중요해서, 대여섯 가지를 실제 크기로 그려 놓고 골랐다 — 줄기를 붙이면 십자로 보이고, 삼각형만 두면 덩어리로 보인다. **꼬리를 V 로 판 화살촉**이 방향이 제일 잘 읽혔다. 모양은 북쪽 하나만 적고 나머지 셋은 `gfx/quest_convert.py` 가 돌려서 만든다 - 네 벌을 손으로 적으면 한 벌만 틀려도 모르고 지나간다.

### 파란색 한 칸을 어디서 구했나

화면 전체가 팔레트 16색을 함께 쓰는데 이 그림에는 **파랑이 한 칸도 없었다**(전부 회색과 크림). 그래서 한 자리를 내줘야 했다.

14번 `(5,4,5)` 를 골랐다. 배경 54,272 픽셀 중 **한 픽셀도** 쓰지 않는 자리였다. 바꾼 뒤 배경 RLE 와 벽면 런을 이전 결과와 바이트 단위로 비교했더니 **둘 다 완전히 같았다.**

그런데 **몬스터 그림에 파란 점 네 개**가 박혔다. 원래 그 자리를 쓰던 픽셀이 있었고, 색을 바꿔도 여전히 그 자리가 제일 가깝다고 뽑힌 것이다. 그래서 `quest_pal.RESERVED` 를 두어 **UI 전용 색은 양자화 후보에서 아예 뺐다.** 팔레트와 양자화 규칙도 `gfx/quest_pal.py` 한 곳으로 모았다 - 그전에는 `quest_convert.py` 와 `quest_rules.py` 가 같은 값을 각자 적어 두고 "서로 같아야 한다"는 주석만 달려 있었다.

### 안개 걷기 — 가 본 자리만 남는다

지도를 열면 층 전체가 보이던 것을, **걸어 본 자리 둘레 3x3 만** 보이게 바꿨다. 움직이거나 제자리에서 돌 때마다 `RevealAround` 가 `(x-1,y-1)`~`(x+1,y+1)` 아홉 칸을 표시한다. 이미 표시된 칸은 다시 쓰지 않는다 — 한 걸음 옮기면 아홉 칸 중 여섯 칸은 직전에 이미 본 자리다.

기록은 256바이트 배열 `SeenRam` 이다. 비트맵으로 하면 32바이트면 되지만, **`MapDataRam` 바로 다음 페이지**에 두는 편을 골랐다. 색인이 `(y<<4)|x` 로 같으므로 미니맵이 한 칸을 그릴 때 주소 계산을 한 번만 하고 `inc h` 한 번으로 지도에서 방문 기록으로 넘어간다. 니블을 꺼내 마스크를 씌우는 것보다 짧다.

```asm
.cell:
    inc h                       ; 같은 칸의 방문 기록
    ld a, (hl)
    dec h
```

안 가 본 칸은 **양피지 색**(`MsgClear` 가 창을 지우는 색과 같다)으로 둔다. 그래서 걸어 다니면 빈 양피지 위로 지도가 조금씩 드러나는 것처럼 보인다.

맵 밖은 부호 없는 비교 하나로 걸러진다 — `x` 가 0 일 때 `x-1` 은 0xFF 가 되는데 `MAP_W` 보다 크므로 그대로 걸린다.

`verify_quest_map.ps1` 이 이것도 확인한다. 알려진 통로를 세 걸음 걷고 `SeenRam` 을 덤프해, 지나온 자리들의 3x3 합집합과 글자 그대로 같은지 본다(세 걸음이면 18칸).

**이 검사는 처음부터 운에 기대고 있었다.** 나중에 갑자기 `(7,7) 에서 끝남, (7,5) 를 기대` 로 떨어졌는데, 안개 코드는 손대지도 않은 때였다. 걸을 때마다 여덟 칸에 한 번꼴로 `RollEncounter` 가 전투를 걸고, 전투가 걸리면 뒤이은 방향키를 이동으로 안 받는다. 세 걸음 중 한 걸음만 들어간 것이다. 그전까지는 주사위가 좋았을 뿐이다. 지금은 `RollEncounter` 입구에 브레이크포인트를 걸어 스택의 복귀 주소로 곧장 되돌린다 - 걷는 동안 전투가 아예 안 걸린다.

> 통과하는 검사도 **왜** 통과하는지 알아야 한다. 이 검사는 "안개가 맞다" 가 아니라 "안개가 맞고 + 난수가 봐줬다" 를 보고 있었다.

## 입력 — 다른 행의 키를 읽는 방법과 함정

M 은 키보드 매트릭스 **4행 bit2** 다. 커서/스페이스는 8행이라 한 번의 `ReadInput` 으로는 같이 읽을 수 없다.

**잘못된 방법(실제로 저질렀다)**: 8행을 읽어 `and 0x0F` 로 하위 비트만 남기고, M 을 bit6 으로 밀어 붙여 하나의 `keyState` 에 합성. → `and 0x0F` 가 **커서키(bit4-7)를 통째로 지워서** "M 은 되는데 이동이 안 되는" 증상이 나왔다.

**옳은 방법**: 8행은 원래대로 전체 바이트를 `keyState` 에, 4행은 `and 0x04` 로 M 만 뽑아 `mKey` 에. 새로-눌림 판정도 `prevKey` / `prevM` 로 각각 따로 한다.

**나중에 하나 더 나왔다 (2026-08-31)**: `HandleInput` 이 새로 눌린 키 비트를 `C` 에 들고 있는데, M 처리에서 부르는 `ToggleMap` → `DrawMap` 이 `ld b, MAP_W` / `ld c, 0` 으로 **BC 를 마음껏 쓴다.** 돌아오면 `C` 가 쓰레기라, **M 을 누르면 그 쓰레기 비트대로 걷거나 돌거나 전투가 걸렸다.** `push bc` / `pop bc` 로 감쌌다. 미니맵을 보는 순간에는 한 칸 움직인 것이 눈에 잘 안 띄어서, 좌표를 메모리에서 읽는 검증 장치가 아니었으면 못 찾았을 것이다.

키 매트릭스(국제 배열, openMSX 실험으로 확인):

| 행 | 키 |
|---|---|
| 4 | bit2 = **M** |
| 6 | bit0 = SHIFT |
| 8 | bit4=← bit5=↑ bit6=↓ bit7=→ bit0=스페이스 |

## RAM 배치

`MapDataRam`(256B), `MiniMapRow`(48B), `MapOn`, `mKey/prevM`, 방 생성 변수들(`RoomCount/Target/Attempts/W/H/X/Y/CX/CY/PrevRoomX/Y`), `MiniMapY/MiniMapScreenY` 를 모두 `RamStart`~`RamEnd` **안쪽**에 두었다. Init 이 이 범위 전체를 0 으로 지우므로(blueMSX 교훈), 켤 때의 쓰레기 값 문제에서 자동으로 안전하다.

## 검증하며 배운 것 (openMSX 21.0 + C-BIOS_MSX2)

- **Init 이 끝나는 데 3~5초 걸린다.** 2초 시점에 메모리를 읽으면 Init 전 쓰레기(posX=0, facing=39 같은 값)를 읽는다. "부팅 실패"로 오인하지 말 것. 검증 스크립트는 5초 후부터 읽는다.
- **이 128KB rom 은 `-romtype ASCII8` 을 붙이면 오히려 부팅이 실패한다**(0x4000 에 뱅크가 어긋나 그래픽 데이터가 읽힘). 빼면 자동 판정으로 정상. README 의 권장과 반대 결과라 이유는 계속 추적 중.
- 좌우 벽 판정 회귀 검증: 맵을 메모리에 직접 써서 (L열림,R벽) (L벽,R열림) (둘 다 열림) (둘 다 벽) 네 상태를 만들고 화면 가장자리 픽셀 프로파일로 판정 — 네 케이스 전부 맵 기대와 일치.
