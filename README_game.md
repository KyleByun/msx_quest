# MSX2 종스크롤 슈팅 데모 (Zanac 스타일)

MSX2 + Z80 어셈블리 + openMSX. Zanac 참고 이미지에서 뽑은 그래픽으로 만든 종스크롤 슈팅 게임입니다. 어셈블리로 작성했을 때 8비트 MSX2가 어느 정도 처리량을 내는지 보는 게 목적입니다.

**동작하는 것**: 스크롤 배경, 자기 이동(커서 키)과 자동 발사, 적기 낙하·좌우 이동·플레이어 조준 사격, 좌상단 fps/CPU 사용량 표시, 우상단 에너지 게이지, 가운데 스코어, 피격/충돌 데미지, 에너지 0에서 GAME OVER, 시간에 따른 난이도 상승, 2분 중간보스와 4분 거대보스, PSG 효과음. **60fps를 놓치지 않습니다.**

화면 배치는 **최상단 줄**에 가운데 정렬 스코어와 오른쪽 에너지 게이지(같은 Y), **그 아래 줄** 좌측에 `F60`(fps) `C58`(CPU 사용량 %)입니다. fps/CPU 줄은 **처음에는 보이지 않고 `0`키로 켜고 끕니다.**

## 사용법

```powershell
.\build.ps1     # src/*.asm -> build/game.rom (16KB)
.\run.ps1       # 빌드 후 openMSX 실행 (창이 뜸)
.\verify.ps1    # 빌드 후 헤드리스로 부팅해 build/screenshot.png 저장

uv run --with pillow python gfx\convert.py   # PNG -> 게임 데이터 재생성
uv run --with pillow python gfx\preview.py   # 생성된 데이터를 그림으로 확인
```

| 키 | 동작 |
|---|---|
| 커서 키 | 이동 (발사는 자동) |
| **0** | fps / CPU 표시 켜기·끄기 (처음에는 꺼져 있음) |
| **1** | 중간보스 즉시 호출 |
| **2** | 거대보스 즉시 호출 |

보스 호출 키는 눌린 순간에만 반응합니다(에지 트리거). 계속 누르고 있어도 보스가 다시 생성되지 않아서, 체력이 리셋되지 않고 정상적으로 깎입니다. 키로 부른 보스는 해당 보스의 시간 트리거를 소모하므로, 나중에 2분/4분이 되어도 같은 보스가 또 나오지는 않습니다.

## 게임 규칙

| 항목 | 값 |
|---|---|
| 에너지 | 32에서 시작. 우상단 게이지 16열(한 열 2포인트). 색이 흰색 → 주황(20 이하) → 빨강(8 이하)으로 바뀌고, 8 이하에서는 점멸 |
| 적 총알 피격 | 에너지 −3 |
| 적기와 충돌 | 에너지 −6, 적기도 함께 파괴 |
| 무적 시간 | 피격 후 48프레임(0.8초) 동안 점멸하며 무적 |
| 점수 | 적기 격추 100점, 보스 명중 10점, 보스 격파 5000점 |
| 게임 오버 | 에너지 0 → 화면 중앙에 GAME OVER, 약 3.3초 뒤 자동 재시작 |

### 난이도 상승

`level`이 512프레임(약 8.5초)마다 오르고 7에서 멈춥니다. 세 가지가 함께 변합니다.

- 동시에 존재할 수 있는 적기 수: `2 + level` (2 → 9)
- 적기 생성 간격: `48 - level*4` 프레임 (48 → 20)
- 적기 발사 간격: `90 - level*8 + 난수(0~31)` 프레임 (점점 짧아짐)

### 보스

| | 등장 | 크기 | 체력 | 패턴 |
|---|---|---|---|---|
| 중간보스 | 7200프레임 (2분) | 32×32 (2×2 셀) | 40 | 좌우 왕복, 단발 |
| 거대보스 | 14400프레임 (4분) | 48×48 (3×3 셀) | 90 | 좌우 왕복, 2연발 |

보스는 **적기용 스프라이트 슬롯 9개를 통째로 가져다 씁니다.** 그래서 보스전 동안에는 일반 적기가 나오지 않습니다. 보스 등장 판정은 보스가 살아 있는 동안 멈추므로, 중간보스를 못 잡으면 거대보스는 나오지 않습니다.

## 그래픽 파이프라인

`gfx/convert.py`가 `images/`의 원본 PNG를 읽어 MSX2 데이터로 변환하고, 확인용 PNG를 새 이름으로 저장합니다.

| 원본 | 변환 결과 | 게임에서 쓰는 것 |
|---|---|---|
| `msx_zanac.png` | `msx_zanac_dither.png` | 자기 3프레임(좌/중/우 뱅크), 총알 2종 |
| `nes_zanac.png` | `nes_zanac_dither.png` | 적기 3종, 중간보스, 거대보스 (모두 상하 반전) |
| `zanac-fortresses.png` | `zanac-fortresses_dither.png` | 배경 타일 16개 + 16×15 맵 |

스코어 숫자, 에너지 게이지, GAME OVER 글자는 원본에 없으므로 `convert.py`가 직접 생성합니다.

변환 결과는 `src/gfxdata.asm`(데이터)와 `src/gfxconst.asm`(상수)로 나옵니다.

### 디더링에 대해

**소재 성격에 따라 다르게 처리했습니다.** 요청은 "MSX에서 쓸 수 있게" 만드는 것이었고, 도트 그래픽에 오차 확산 디더링을 거는 것은 그 목적에 반하기 때문입니다.

- **스프라이트 시트 2장은 최근접 색상 매핑만 했습니다 (디더링 없음).** 원본이 이미 8~11색 도트 그래픽이라 MSX2의 RGB333 공간에 거의 그대로 들어갑니다. 16×16 스프라이트에 디더링을 걸면 실루엣에 노이즈가 흩뿌려져 오히려 망가집니다.
- **요새 스크린샷은 4×4 Bayer 순서 디더링을 씁니다.** 19색이라 15칸에 안 들어가서 4색이 병합되고, 그 손실을 디더링이 메웁니다. Floyd-Steinberg 같은 오차 확산이 아니라 순서 디더링을 쓰는 이유는, 오차 확산은 타일 경계를 넘어 이어지지 않아서 스크롤할 때 16픽셀마다 이음매가 드러나기 때문입니다.

**팔레트는 이미지마다 따로 만듭니다.** 게임 팔레트를 미리보기 이미지에 그대로 쓰면 안 됩니다 — 게임은 우상단 사분면 타일만 쓰므로 팔레트에 녹색이 없고, 요새 이미지 4장 중 3장이 녹색 계열이라 전부 올리브색으로 뭉개집니다. 실제로 처음에 그렇게 나왔습니다.

게임 팔레트는 **게임이 실제로 쓰는 소재만** 놓고 만듭니다(13색이라 병합 없음). SCREEN 5는 화면 전체가 팔레트 16색 하나를 공유하므로 — 스프라이트용 16색 + 배경용 16색이 아닙니다 — 스프라이트와 배경 소재를 한꺼번에 놓고 만듭니다. 0번은 스프라이트 투명색이자 border 색이라 그림에는 쓰지 않습니다.

### 배경 타일 추출

`zanac-fortresses.png`는 스크린샷 4장이 2×2로 붙어 있는 이미지입니다. 그중 우상단(검정 바탕 + 노란 격자)이 가장 타일 규칙성이 높아서(16×16 블록 240개 중 50종) 이걸 씁니다.

격자 위상이 (0,0)에 맞아 있지 않기 때문에, 16×16 오프셋을 전부 시도해서 서로 다른 블록 수가 최소가 되는 지점을 찾습니다 — (1,1)이었습니다. 그다음 배경에 없는 색(흰색 HUD 글자, 스프라이트의 파랑·분홍)이 섞인 블록을 걸러냅니다. 50종 중 29종이 이렇게 탈락하고, 남은 것 중 빈도 상위 16개를 씁니다. 탈락한 블록이 놓인 맵 자리는 가장 비슷한 정상 타일로 대체해서 요새 배치가 무너지지 않게 합니다.

## 기술 구조

### 배경 스크롤 — VDP가 공짜로 해줍니다

SCREEN 5의 VRAM 페이지 0은 32KB = **256라인**인데 화면에는 212라인만 보입니다. R#23(수직 스크롤)으로 표시 시작 라인을 옮기면 하드웨어가 스크롤을 처리하고, CPU는 아무것도 그리지 않습니다.

남는 44라인이 화면 밖 여유분입니다. CPU가 매 프레임 하는 일은 **곧 화면에 들어올 픽셀 라인 하나(128바이트)를 타일에서 찍어내는 것**뿐입니다. 약 3.7k T-state로, 수직 귀선 기간 안에 끝납니다.

- 스크롤 값은 매 프레임 **감소**합니다. 표시 창이 VRAM 위쪽으로 올라가므로 지형은 아래로 흐르고, 플레이어가 전진하는 그림이 됩니다.
- 그릴 대상 라인은 항상 `(scroll - 13)`으로, **방금 R#23에 쓴 값에서 계산합니다.** 별도 카운터를 돌리면 프레임이 한 번이라도 밀렸을 때 스크롤과 어긋나 영구적으로 화면이 찢어집니다.
- 타일 데이터는 256바이트 정렬해 두어서, 타일의 한 픽셀 행 주소를 8비트 연산만으로 구합니다 (`tile*128 = (tile>>1)*256 + (tile&1)*128`).

VRAM 페이지 0을 256라인 전부 비트맵으로 쓰기 때문에 **스프라이트 테이블은 페이지 1(0x9400~)에 둡니다.** 페이지 0에 두면 어떤 스크롤 위치에서는 스프라이트 테이블이 화면에 그림으로 표시됩니다. 그래서 이 데모는 VRAM 128KB(표준 MSX2)가 필요합니다.

### R#23은 스프라이트도 같이 끌고 갑니다 — 함정 두 개

**함정 1.** V9938에서 수직 스크롤 레지스터는 비트맵뿐 아니라 **스프라이트 평면도 같이 밀어버립니다.** 속성에 Y라고 적힌 스프라이트는 화면 `Y + 1 - R#23`번 라인에 그려집니다. 그래서 가만히 있어야 할 자기가 배경 스크롤을 따라 화면 위로 흘러갑니다. 실제로 이 데모도 처음에 그랬고, `scroll=43`일 때 `Y=160`인 자기가 118번 라인에 그려지는 것을 확인했습니다.

해결은 **모든 스프라이트 Y에 현재 스크롤 값을 더해주는 것**입니다 (`BiasY`).

**함정 2.** 속성 Y가 **216이면 스프라이트 목록의 끝**을 의미합니다. 보정 결과가 216이 되면 그 프레임에서 뒤쪽 스프라이트가 **전부** 사라집니다. `playerY=160`이면 `scroll=56`일 때 정확히 216이 되므로, 256프레임마다 한 번(약 4.3초마다) 화면의 모든 스프라이트가 한 프레임 사라집니다. 한 프레임짜리라 스크린샷으로는 거의 안 잡힙니다.

그래서 `BiasY`는 보정 결과가 216이면 1을 빼서 비켜갑니다. 1픽셀 어긋나는 것은 안 보이지만 스프라이트가 사라지는 것은 보입니다.

### 스프라이트 배치

하드웨어 스프라이트 모드 2를 씁니다. 모드 2는 **한 스캔라인에 색 하나**뿐이라, 여러 색인 자기는 평면 두 장으로 나눕니다. `sprite_layers()`가 각 라인마다 가장 많은 색 두 개를 골라 A/B 평면에 나누고, 세 번째 색은 둘 중 가까운 쪽에 흡수시킵니다. **두 평면은 픽셀이 겹치지 않기 때문에** CC(OR 합성) 비트가 필요 없습니다 — 일반 우선순위만으로 정확히 합쳐집니다.

총알과 보스 셀은 평면 하나만 씁니다. 총알은 검은 외곽선을 투명 처리했습니다 — 라인당 한 색뿐이라 외곽선이 그 라인의 최다 색으로 뽑히면 검은 배경에서 총알이 안 보이게 됩니다.

슬롯 32개를 전부 씁니다:

| 슬롯 | 용도 |
|---|---|
| 0–5 | 스코어 6자리 |
| 6 | 에너지 게이지 |
| 7 | `F` 라벨 |
| 8–9 | fps 2자리 |
| 10 | `C` 라벨 |
| 11–12 | CPU 사용량 2자리 |
| 13–14 | 자기 (본체 평면 + 디테일 평면) |
| 15–18 | 자기 총알 4발 |
| 19–27 | 적기 9기 **또는** 보스 셀 |
| 28–31 | 적 총알 4발 |

**모드 2는 한 스캔라인에 8개까지만 그리고, 9번째부터는 깜빡이는 게 아니라 슬롯 순서대로 그냥 안 그립니다.** 그래서 **HUD를 슬롯 0번부터 배치했습니다.** 우선순위가 가장 높아서 절대 사라지지 않고, 그 줄이 붐비면 게임 오브젝트가 대신 밀립니다.

**HUD를 두 줄로 나눈 것도 이 8개 제한 때문입니다.** 한 줄에 다 몰면 `F`1 + fps2 + `C`1 + CPU2 + 스코어6 + 게이지1 = **13개**라 5개가 소리 없이 잘립니다.

| 줄 | 위치 | 내용 | 개수 |
|---|---|---|---|
| 1 (3번 라인) | 가운데 / 오른쪽 | 스코어 / 에너지 게이지 | 7 |
| 2 (19번 라인) | 왼쪽 | `F` fps, `C` CPU (`0`키 토글) | 6 |

스코어와 게이지를 같은 줄에 둬서 Y가 맞습니다. 두 띠(3~34번 라인)에는 HUD만 들어오도록 강제합니다 — 적기와 보스는 **36번 라인** 아래에서만 등장하고, 자기 총알은 36번 라인에 닿으면 사라집니다. **이 경계는 fps/CPU 줄을 껐을 때도 그대로**라, 토글해도 플레이 영역이 움찔거리지 않습니다.

fps/CPU는 꺼져 있어도 **측정은 계속합니다.** 슬롯만 화면 밖으로 치울 뿐이라, 켜는 순간 바로 현재 값이 나옵니다.

HUD가 슬롯 13개를 가져가면서 적 총알은 6→4발, 에너지 게이지는 2칸(32열)에서 1칸(16열, 한 열이 2포인트)으로 줄었습니다. 자리를 만들려고 **적기 상한을 12→9로 낮췄는데, 난이도 램프의 최대치가 원래 `2 + level(7) = 9`라 게임 플레이상 손해는 없습니다.** 대신 보스 격자도 그 안에 들어와야 해서 거대보스가 3×4에서 3×3으로 작아졌습니다.

### HUD 글자를 어디에 놓을지

배경이 세로로만 스크롤하므로 **어떤 X도 결국 모든 맵 행을 만납니다** — 항상 검은 자리는 없습니다. 그래서 맵 전체에 대해 각 19픽셀 구간이 어두운 비율을 계산해서 자리를 골랐습니다.

| 위치 | 배경이 어두운 비율 |
|---|---|
| x=6 (`F` 판독) | 77% |
| x=48 (`C` 판독) | 76% |
| x=30 (처음 골랐던 자리) | **48%** |

처음에 `C`를 x=30에 뒀더니 요새 기둥에 정확히 걸쳐서 숫자가 안 읽혔습니다. x=48로 옮기니 해결됐습니다. 스코어는 가운데 정렬이 요구사항이라 x=110 고정(57%)입니다.

폰트는 HUD 숫자만 **5×7**로 줄였습니다(예전 8×8). GAME OVER 글자는 헤드라인이라 8×8 그대로입니다.

게임 오버 화면에서는 오브젝트가 전부 없으므로, 슬롯 11~18을 빌려 GAME OVER 글자를 표시합니다. 빌린 슬롯의 색 테이블은 그때 흰색으로 칠하고 재시작할 때 되돌립니다.

### 대형 스프라이트는 어떻게 만들었나

**MSX2 하드웨어 스프라이트는 16×16이 최대입니다.** 그보다 큰 것은 하드웨어가 지원하지 않습니다. (R#1의 MAG 비트로 32×32까지 확대할 수 있지만 이건 전역 설정이라 자기·총알까지 전부 두 배가 됩니다. 쓸 수 없습니다.)

그래서 보스는 **16×16 스프라이트를 격자로 붙여서** 만듭니다. 거대보스는 3×4 = 12장, 중간보스는 3×2 = 6장입니다. 하드웨어 입장에서는 그냥 독립된 스프라이트 12개가 나란히 놓여 있는 것이고, "큰 스프라이트"라는 개념은 코드 쪽에만 있습니다.

**변환 단계** (`gfx/convert.py`의 `slice_cells`) — 원본 PNG에서 보스를 잘라내 격자 크기(48×64)에 맞춰 가운데 정렬한 뒤, 16×16 칸으로 썰어서 각 칸을 독립된 스프라이트 패턴으로 만듭니다. 패턴 번호는 왼쪽 위부터 행 우선으로 연속 배치됩니다.

**런타임** (`BuildBossCells`) — 커서 (X, Y)를 놓고 격자를 훑으면서 칸마다 속성 한 줄씩 씁니다:

```
셀 (col, row) -> X = bossX + col*16
                 Y = bossY + row*16
                 패턴 = 첫 패턴 번호 + row*3 + col
```

한 행이 끝나면 X를 `bossX`로 되돌리고 Y를 16 더합니다. 보스가 움직이면 12개 속성이 전부 다시 계산되지만, 어차피 매 프레임 스프라이트 테이블 전체를 다시 만들기 때문에 추가 비용은 없습니다.

**설계상 제약 세 가지:**

1. **슬롯을 어디서 가져오나** — 32개를 이미 다 쓰고 있어서 보스용으로 새로 낼 자리가 없습니다. 그래서 보스는 **적기용 슬롯 12개를 통째로 빌려 씁니다.** 보스가 뜨면 살아 있던 적기를 전부 지우고, 보스전 동안에는 적기가 생성되지 않습니다.
2. **가로 폭은 8칸이 한계** — 모드 2는 한 스캔라인에 스프라이트를 8개까지만 그립니다. 보스를 가로로 8칸(128픽셀) 넘게 만들면 그 줄에서 잘립니다. 3칸이라 같은 줄에 5개 여유가 남습니다.
3. **칸마다 색은 라인당 하나** — 자기는 평면 두 장을 겹쳐 여러 색을 내지만, 보스는 12칸 × 2평면 = 24개라 슬롯이 모자랍니다. 그래서 보스 칸은 평면 하나만 쓰고, 각 스캔라인의 색은 그 줄에서 가장 많은 색으로 정해집니다.

**충돌 판정은 격자와 무관합니다.** 칸마다 검사하지 않고 보스 전체를 사각형 하나(`BossWidth` × `BossHeight`)로 보고 총알과 비교합니다. 아홉 번 검사할 이유가 없습니다.

**격자 크기는 `gfx/convert.py`가 소유합니다.** 원본을 자르는 쪽이 격자를 정하므로 `MBOSS_COLS/ROWS`, `GBOSS_COLS/ROWS`를 `gfxconst.asm`으로 내보내고 게임은 그걸 씁니다.

한 번 이 값을 양쪽에 따로 두었다가 실제로 어긋난 적이 있습니다. 변환 쪽은 3×3으로 자르는데 게임 쪽은 3×4로 알고 있어서, 존재하지 않는 보스 셀 3개를 그리려다 **패턴 번호가 숫자 글리프 영역으로 넘어가 화면에 "0 1 2"가 떠다니고**, 슬롯 배열까지 넘어 써서 게임이 프레임을 놓치기 시작했습니다(HUD가 `F00` `C99` 빨강). 그래서 빌드 시점에 막도록 단언을 넣었습니다:

```
ASSERT MBOSS_COLS * MBOSS_ROWS <= MAX_EN, mid-boss needs more slots than MAX_EN
ASSERT GBOSS_COLS * GBOSS_ROWS <= MAX_EN, giant boss needs more slots than MAX_EN
```

`MAX_EN`을 8로 낮춰 실제로 빌드가 멈추는 것까지 확인했습니다.

### 에너지 게이지 색

게이지 색은 패턴에 박아 넣지 않고 **코드에서 색 테이블에 씁니다.** 팔레트에 초록 계열이 요새 타일과 같은 올리브 하나뿐이라, 패턴 색을 그대로 쓰면 게이지가 배경에 묻혀 안 보였습니다(처음에 실제로 그랬습니다). 지금은 남은 양에 따라 흰색/주황/빨강으로 바뀌고, 값이 바뀔 때만 다시 씁니다.

### 사운드

PSG 채널 A는 피격 시 떨어지는 톤, 채널 B는 격추 시 노이즈 버스트를 냅니다. 둘 다 프레임마다 한 번 갱신하는 원샷 엔벨로프입니다.

R7(믹서)은 MSX에서 **항상 `10xxxxxx`여야 합니다** — bit7이 포트 B를 출력(조이스틱 선택)으로, bit6이 포트 A를 입력으로 유지합니다. 여기서는 톤 A와 노이즈 B만 켠 `0xAE`를 씁니다.

### fps / CPU 사용량 측정

예전에는 프레임 작업 동안 border(R#7)를 빨갛게 칠해서 좌우 테두리의 빨간 띠 높이로 CPU 시간을 보여줬습니다. 지금은 그 띠를 없애고 **숫자로 표시**합니다.

**CPU 사용량은 vblank를 기다리는 시간을 세서 구합니다.** 프레임 작업이 끝나면 어차피 vblank까지 놀아야 하는데, 그 대기 루프에서 회전 수를 세면 그게 곧 남은 시간입니다. 대기 루프 한 바퀴를 정확히 **597 T-state**가 되도록 패딩했습니다:

```
inc de 6 + ld b,43 7 + djnz x43 554 + in 11 + and 7 + jr 12 = 597
```

60Hz 프레임은 3579545/60 = 59659 T-state이고, 59659/597 = **99.9**입니다. 즉 완전히 노는 프레임이면 카운트가 100이 나오도록 맞춰둔 것이라, **나눗셈 없이 카운트가 곧 여유 퍼센트**이고 `100 - 카운트`가 사용량입니다. R#9로 VDP를 60Hz 모드에 두기 때문에 PAL 기기에서도 같은 값이 나옵니다.

**fps는 놓친 마감으로 셉니다.** 루프가 vblank에 물려 있으니 프레임을 흘리지 않는 한 항상 화면 주사율로 돕니다. 그래서 대기에 들어갔을 때 **이미 vblank 플래그가 서 있으면** 그 프레임은 마감을 넘긴 것으로 세고, 60프레임마다 `60 - 늦은 횟수`를 표시합니다.

두 숫자가 나란히 있고 평소엔 둘 다 60이라 헷갈리므로 **색으로 구분**합니다. 스프라이트를 더 쓰지 않고 색 테이블만 바꾸면 되니 공짜입니다.

| | 흰색 | 하늘색 | 주황 | 빨강 |
|---|---|---|---|---|
| fps (왼쪽) | 60 정상 | | | 60 미만 (프레임 누락) |
| CPU (오른쪽) | | 70% 미만 | 70~89% | 90% 이상 |

측정값 (에뮬레이터 메모리에서 직접 확인):

| 상황 | 여유 카운트 | CPU |
|---|---|---|
| 일반 플레이 | 42 | 58% |
| 거대보스 등장 | 35 | 65% |

`100 - 여유 = CPU`가 정확히 맞습니다. 화면 표시는 0.5초마다 갱신하므로 순간값과 몇 % 차이가 날 수 있습니다. 예전 border 방식으로 잰 57~61%와도 일치해서, 두 방식이 서로를 검증해 줍니다.

**60fps는 일반 플레이와 보스전 양쪽에서 확인했습니다** — 1초 동안 프레임 카운터가 정확히 60 증가하고, 놓친 마감 카운터는 0입니다.

재시작 순간은 한 프레임에 색 테이블을 몰아 쓰기 때문에 따로 확인했습니다. 게임 오버 정지 구간을 뺀 스크롤 진행량이 경과 시간과 맞아떨어져서, 프레임을 흘린 흔적은 없습니다. 다만 이쪽은 폴링 간격 때문에 ±3프레임 정도의 오차가 있는 측정이라, 위의 두 경우처럼 정확히 60이라고는 말하지 않겠습니다.

### 어트랙트 모드

아무도 조작하지 않으면 자기는 가만히 서 있다가 30초쯤 만에 격추되고, 데모는 게임 오버 화면에서 시간을 보냅니다. 그래서 **날아오는 적 총알을 피해 좌우로 움직이는 간단한 자동 조종**을 넣었습니다. 실제 키를 한 번이라도 누르면 영구히 꺼집니다.

다만 이 자동 조종은 **적 총알만 피하고 적기 자체는 피하지 않아서** 보통 1분 남짓 버팁니다. 즉 방치해서는 2분 보스까지 가지 못합니다. 보스를 보려면 직접 플레이하거나, 아래 방법으로 시계를 앞당기면 됩니다.

### 그 외

- **인터럽트를 쓰지 않습니다.** `di` 상태로 VDP 상태 레지스터 S#0의 vblank 플래그를 폴링합니다. S#0은 읽으면 플래그가 지워지므로 인터럽트 핸들러가 먼저 읽어가면 폴링이 깨집니다.
- **충돌 판정은 소프트웨어**입니다. VDP의 충돌 플래그는 "뭔가 겹쳤다"만 알려주고 무엇과 무엇인지는 알 수 없어 쓸모가 없습니다. 8비트 랩어라운드를 이용한 `(b - a + 절반) < 폭` 관용구로 부호 비교 없이 처리합니다.
- **ROM이므로 자기 수정 코드를 쓸 수 없습니다.** 모든 가변 상태는 페이지 3 RAM(0xC000~)에 있습니다.
- 스코어는 BCD 6자리(바이트당 한 자리)로 들고 자리올림만 전파합니다. 이진수로 두고 10으로 나누는 것보다 싸고, 그대로 스프라이트 패턴 번호가 됩니다.
- 스프라이트 패턴은 16×16 기준 **64개가 하드웨어 상한**입니다(패턴 번호가 8비트, 하나가 4개를 소모). 현재 63개를 씁니다. `convert.py`가 초과하면 빌드를 세웁니다.

## 소스 파일 인코딩

`.asm`의 주석은 한글이고, 파일은 전부 **BOM 없는 UTF-8**입니다.

sjasmplus는 주석을 줄 끝까지 그냥 건너뛰므로 한글이 들어가도 문제가 없습니다. 실제로 같은 코드에 영문 주석 / 한글 주석 / 한글 주석+BOM 세 가지로 어셈블해서 **출력 바이너리가 완전히 동일한 것**을 확인했습니다. 즉 BOM이 있어도 어셈블 자체는 되지만, 굳이 붙일 이유가 없어 BOM 없이 저장했습니다.

주의할 점 하나: **`gfx/convert.py`가 `.asm`을 쓸 때 `encoding="utf-8"`을 명시해야 합니다.** 빼먹으면 파이썬이 콘솔 코드페이지로 쓰려다 한글에서 `UnicodeEncodeError`가 나고 생성 파일이 깨집니다 (실제로 한 번 겪었습니다).

편집기가 파일을 CP949로 다시 저장하지 않게 UTF-8로 열어 주세요. 어셈블은 그래도 되지만 다른 도구에서 글자가 깨져 보입니다.

## 디버깅 요령

openMSX의 Tcl로 메모리를 직접 건드리면 오래 기다리지 않고 확인할 수 있습니다.

**주소를 코드에 적어두지 마세요.** 변수를 하나만 추가해도 뒤쪽 주소가 전부 밀립니다. 실제로 이것 때문에 한 번 엉뚱한 곳을 읽고 검증 결과를 잘못 해석했습니다. 빌드할 때마다 심볼 파일에서 읽으면 됩니다:

```powershell
Select-String -Path build\game.sym -Pattern "^(frameCount|energy|demoMode|gameState|bossActive|scroll):"
```

그렇게 얻은 주소로:

```tcl
# 중간보스를 바로 부르기: frameCount를 7190으로 (2분 = 7200프레임)
debug write memory <frameCount>     0x16
debug write memory <frameCount + 1> 0x1C

debug write memory <energy>   32     ;# 에너지 채우기
debug write memory <demoMode> 0      ;# 자동 조종 끄기

screenshot -raw -size auto "shot.png"   ;# 창 없이 스크린샷
```

## 구성

```
src/main.asm       게임 본체
src/gfxdata.asm    생성됨 - 팔레트/스프라이트/타일/맵 데이터
src/gfxconst.asm   생성됨 - 패턴 번호 등 상수
src/skeleton.asm   참고용 최소 예제 (빌드에 포함되지 않음)
gfx/convert.py     PNG -> MSX2 데이터 변환
gfx/preview.py     생성된 데이터를 렌더링해서 확인 (gfx/preview.png)
images/            원본 PNG와 변환된 PNG
tools.ps1          툴체인 경로
build.ps1 / run.ps1 / verify.ps1
```

`gfx/preview.py`는 원본 PNG가 아니라 **생성된 asm 데이터를 다시 읽어서** 그림을 만듭니다. 그래서 스프라이트 평면 분리 오류, 타일 바이트 순서 실수, 맵 인덱스 어긋남 같은 변환 자체의 버그가 드러납니다.

## 고쳤던 버그 중 기억할 만한 것

**서브루틴이 BC를 뭉갠 탓에 적 총알이 허공에서 나왔습니다.** "적기가 없는 곳에서도 총이 나온다"는 제보로 찾았습니다.

`RandomFireDelay`가 내부 계산에 B와 C를 임시로 썼는데, 호출하는 쪽 두 군데(`UpdateEnemies`의 발사 처리와 `SpawnEnemy`)는 **BC에 적기 인덱스를 담은 채로** 이 루틴을 부르고 돌아온 직후 그 BC로 배열을 인덱싱했습니다. 그래서 발사한 적기의 X·Y를 수천 바이트 떨어진 엉뚱한 주소에서 읽어왔습니다.

증상이 정확히 "허공에서 발사"였던 이유는, 그 엉뚱한 주소가 매번 거의 같은 값이라 총알이 (52,53)이나 (52,2) 같은 **고정된 좌표에서 반복해서 생겨났기** 때문입니다.

에뮬레이터로 총알이 생기는 순간마다 가장 가까운 적기까지의 거리를 재서 확인했습니다:

| | 관측된 총알 | 적기 위에서 생성 | 허공에서 생성 |
|---|---|---|---|
| 수정 전 | 13 | **0** | **13** |
| 수정 후 | 26 | **26** | 0 |

`push bc` / `pop bc` 한 쌍으로 끝나는 문제였습니다. 같은 시간 동안 관측된 총알 수가 13→26으로 는 것은, 발사 간격 값도 엉뚱한 주소에 쓰이고 있어서 발사 주기 자체가 망가져 있었기 때문입니다.

**교훈**: 인덱스를 레지스터에 담아 배열을 훑는 루프 안에서 서브루틴을 부를 때는, 그 루틴의 레지스터 파괴 목록을 반드시 확인해야 합니다. 이 프로젝트의 다른 헬퍼들(`Random`, `BiasY`, `PutSlot`, `HideSlot`, 보스 크기 조회 루틴들)은 BC를 보존하도록 되어 있고, 파괴하는 것들(`SetSlotColour`, `AddScore`, `FillSlotColour`, `DamagePlayer`)은 호출부가 push/pop로 감싸고 있습니다 — 이 건만 빠져 있었습니다.

## 아직 없는 것 / 알려진 한계

1. **스프라이트 속성 전송이 귀선 밖에서 일어납니다 — 실제로 확인된 문제입니다.** 프레임 작업이 끝난 뒤에 128바이트를 쓰기 때문에 VDP가 테이블을 읽는 중에 갱신될 수 있고, 그러면 그 프레임만 앞쪽 슬롯은 새 내용, 뒤쪽 슬롯은 이전 내용으로 섞여 보입니다.

   게임 오버에서 재시작하는 순간을 캡처했더니 실제로 잡혔습니다 — 자기와 스코어는 이미 새 프레임인데 GAME OVER 글자가 아직 남아 있는 화면이 한 프레임 나왔습니다. 슬롯이 한꺼번에 많이 바뀌는 순간이라 가장 잘 드러납니다. 0.1초 뒤 프레임은 정상입니다.

   고치려면 **이번 프레임에 만든 것을 다음 프레임 귀선에 보내면** 됩니다. 그때는 스크롤이 한 칸 더 진행된 뒤에 표시되므로 `yBias`를 `scroll - 1`로 잡아야 합니다.
2. **폭발 연출이 없습니다** — 적기가 그냥 사라집니다. 사운드만 납니다.
3. **잔기 개념이 없습니다** — 에너지 0이면 바로 게임 오버, 자동 재시작합니다.
4. **스프라이트 우선순위 로테이션이 없습니다** — 한 라인에 9개 이상 몰리면 슬롯 번호가 큰 것이 사라집니다.
5. **맵 이음매** — 15행 맵이 반복되므로 240라인마다 14행→0행 경계가 보일 수 있습니다.
6. **적기가 화면 끝에서 방향을 뒤집을 때 한 프레임 범위를 벗어납니다** (자체 복구되며 216에는 닿지 않음).
7. **BGM이 없습니다** — 효과음만 있습니다. PSG 채널 C가 통째로 비어 있습니다.
